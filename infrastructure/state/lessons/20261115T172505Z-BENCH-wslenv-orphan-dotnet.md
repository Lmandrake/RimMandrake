From WSL, an environment variable reaches a Windows exe (python.exe, dotnet.exe) only when WSLENV names it; otherwise the exe silently runs on its defaults while the command line looks right. Measured four ways: a build switch passed by env to dotnet.exe silently did nothing (GSS allfix 2026-11-09); a bridge script under python.exe reading os.environ ran on its defaults and wrote a run's data into the previous run's folder (Graffiti walk 2026-11-14); a GSS Diag run under dotnet.exe with PTS=1 printed nothing until WSLENV=PTS (gss_last, 2026-11-15); ALLROWS=1 python3 diag.py ... (dotnet.exe running diag.py's Diag.dll) printed no twin rows until run as ALLROWS=1 WSLENV=ALLROWS (2026-11-15).
The /u flag is not safe for python.exe: 'WSLENV=MODCHECK_KEEP_MODLIST/u' did NOT deliver the variable to python.exe (WindowsApps alias) on Archmagi 2026-11-15; plain 'WSLENV=MODCHECK_KEEP_MODLIST' did (measured with python.exe -c print(os.environ.get(...)), on WEB_SIEGE_DESIGN_SPIDERS_BRING_SHADE). The cost: modcheck run silently took the non-keep path, swapped ModsConfig to MINIMAL and its finally restored FULL (316 mods) onto disk. So the form WSLENV=VAR/u (once given here as the example) is not the one to use: pass env to a Windows exe as 'env WSLENV=A:B A=1 B=1 python.exe ...' (testq.py does it this way) or export WSLENV=VAR1:VAR2, check the effect, not the command, and code that needs such a variable fails by name when it is missing.
Also, killing the WSL /init wrapper of a dotnet.exe run leaves the Windows process alive and holding bin/*.dll (the next selftest build fails MSB3027): find it by command line with powershell Get-CimInstance Win32_Process and taskkill /PID it (never /IM, which kills every dotnet).
