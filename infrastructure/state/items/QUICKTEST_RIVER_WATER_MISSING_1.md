## spec
No design doc — this is an engine/tooling investigation, not a content build.
Discovered as a side effect of `FISH_BESTIARY_BUILD_1`'s live verification
pass (2026-09-18): every attempt to generate a fresh map at a world tile that
carries a river or a lake-type `TileMutatorDef` produced a map with **zero**
water-family terrain anywhere on it, across every biome tried.

## what was measured
Method: `jawa/colony_found` (Player faction, some runs) or bare
`jawa/world_tile_map_generate` (other runs, no difference observed) at a
tile confirmed via `jawa/world_tile_get` to carry `riverCount > 0` or a
lake-type mutator (`ToxicLake` etc, via `jawa/world_mutators_get`), then a
full-map `jawa/get_terrain_batch` scan (13 row-bands of `0,z,325,25`,
`cellsRead` summing to the exact `sizeX*sizeZ`, so no gap in coverage) for
any terrain name containing "water".

| tile | biome | riverCount / mutator | water cells found |
|---|---|---|---|
| 8501 | RUT_Greentide | riverCount 2 | 0 (of 105625 cells) |
| 2020 | RUT_Greentide | riverCount 2 | 0 (of 105625 cells) |
| 11183 | RUT_Wasteland | riverCount 0 (bad pick) | 0 — expected |
| 224 | RUT_Wasteland | `ToxicLake` mutator | 0 (of 105625) — no
  `RUT_BrineDeposit_*` scattered either, `jawa/list_things` 0 of 9992 scanned |
| 1535 | RM_FE_Pyrelands (non-Ash'karr, non-`RUT_` control) | riverCount 4 | 0 |
| 1214 | RUT_RustCathedral (fishing wiring already independently confirmed
  correct — `FISH_BESTIARY_BUILD_1` wave 5) | riverCount 2 | 0 |

Six tiles, five different biomes, one deliberately non-`RUT_` control
(`RM_FE_Pyrelands`) to rule out "something about our own biomes" — all six
came back with **zero** water terrain. `RUT_RustCathedral` is the load-bearing
result: its fishing mechanism was already read and confirmed correct in the
XML, so a live map for it SHOULD show a river; it did not.

**Positive control, same session, same tools:** `RUT_TheScald` (a whole-tile
"isWaterBiome" ocean-type biome, not a land biome with an embedded river)
DID correctly show real water terrain (`RUT_ScaldWaterOceanDeep`, sampled at
8 points across its whole map plus confirmed via `rimworld/apply_architect_
designator`'s own placement-rejection check). This proves `get_terrain_batch`
and `get_cell_info` DO correctly report water terrain when the game has
actually placed it — the six zero-water results above are not a read-side
blind spot.

**Historical positive control (different session, `references/traps.md`
"A `world_tile_map_generate`'d map can render as a blank void"):** on
2026-09-13, the SAME tool (`world_tile_map_generate`) on `ZBiome_Grasslands`
with `riverCount: 2` DID produce real `WaterMovingShallow` cells via
`get_terrain_batch`. So this tool has worked for a river tile before —
something changed between then and now, or something is specific to
tonight's session/mod state.

## what this blocks
`FISH_BESTIARY_BUILD_1`'s live-verification pass could not conclude PASS or
FAIL for Wasteland (mining), Cracked Lands, Weeping Stones or Greentide
(fishing) this session — not because their own XML wiring is wrong (three of
the four were already re-confirmed correctly wired onto their live BiomeDefs
in prior waves), but because no shallow/deep water of ANY kind materializes
on a freshly generated map to test against. The Wasteland brine-deposit
GenStep scatter is confirmed a casualty of the same root cause (scatters onto
a terrain TAG that only exists on the brine terrain family, which never
generates).

## ROOT CAUSE — FOUND, and it is OURS (FOUNDRY, 2026-09-18)

🔴 **There is no water terrain in the game at all.** Nine `TerrainDef`s —
`WaterShallow`, `WaterDeep`, `WaterMovingShallow`, `WaterMovingChestDeep`,
`WaterOceanShallow`, `WaterOceanDeep`, `ToxicWaterShallow`, `ToxicWaterDeep`
and `Marsh` — **do not exist in the loaded game**. They are discarded during
def loading, every launch, by our own FlowWorks mod.

**The chain, each link measured, none inferred:**

1. `src/RimMandrake/FlowWorks/Patches/LiquidTypes/RM_LiquidProperties_CompatIndex.xml`
   (GENERATED by `src/RimMandrake/FlowWorks/Tools/generate_liquid_suite.py`)
   adds an `RM_LiquidProperties` modExtension carrying
   `<viscosityClass>water</viscosityClass>` — **lowercase** — onto exactly
   those nine defs.
2. The C# enum `RimMandrake.FlowWorks.LiquidTypes.LiquidViscosityClass`
   (`Source/LiquidTypes/RM_LiquidProperties.cs`) has members `Thin, Water,
   Thick, Heavy`. `Verse.ParseHelper.FromString` calls `System.Enum.Parse`
   **case-sensitively**, so `"water"` throws.
3. The throw happens inside the `modExtensions <li>`, and the stack shows
   `DirectXmlToObjectNew...ParseAndReturnDef_Verse_TerrainDef` — RimWorld
   **discards the entire target def** rather than degrading. This is the
   documented `modextension-missing-type-discards-def` class, triggered here
   by a bad enum VALUE rather than a missing type.
   Player.log, verbatim: `Exception loading def from file Terrain_Water.xml:
   System.ArgumentException: Exception parsing ...LiquidViscosityClass from
   "water" ---> 'water' is not a valid value ... Valid values are: • Thin
   • Water • Thick • Heavy`.
4. With those defs gone, **every land BiomeDef's water fields resolve to
   null** — measured on `RUT_Greentide`, `RUT_Wasteland`, `RUT_TheRot`,
   `RUT_AridShrubland`, `RM_FE_Pyrelands`: `waterShallowTerrain`,
   `waterDeepTerrain`, `waterMovingShallowTerrain` and
   `waterMovingChestDeepTerrain` are all `null`.
5. So the river/lake/coast `TileMutatorWorker`s run correctly, compute their
   channel, and then paint it with a **null** terrain — which is the
   thousands of `Tried to set terrain at (x, 0, z) to null.` lines in
   Player.log, in contiguous horizontal bands (a river channel). That spam
   also hit `Reached max messages limit. Stopping logging to avoid spam.`,
   which is why the log went dead at 03:15 and looked uninformative.

**Controlled confirmation.** The patch's target list is exactly the missing
set — 9 of 9 missing. `ToxicWaterOceanDeep` and `ToxicWaterMovingShallow`
are Odyssey water terrains the patch does NOT target, and both are present;
so are `Gravel`, `Sand`, `MarshyTerrain`, `Riverbank`. Zero false positives,
zero false negatives.

**Both of the original puzzles fall out of this:**
- `RUT_TheScald` showed correct water because it defines its own
  `RUT_ScaldWater*` terrains, which the patch does not target.
- The 2026-09-13 `ZBiome_Grasslands` positive control predates the
  liquids-framework patch reaching the deployed mod.

**Suspects cleared, so nobody re-walks them:** `EnvironmentalHazards`, the
rot-wave restart cycle and `gizkastowaway` are all innocent. Geological
Landforms' `Odyssey_DisabledTileMutators` really does list `River`,
`RiverDelta`, `Headwater`, `RiverIsland`, `RiverConfluence` (a non-default
setting — the shipped default is an empty list), but it is NOT the cause:
`Coast` and `Lake` tiles, which it does not disable, are equally waterless.
Map Designer's mutator stripper never fires (`"Try Add Mutators"` appears
zero times in the log). `TILEGEN_SILENT_REUSE_1` is unrelated.

## is it a bridge-tool artifact? NO — it affects normal play

`jawa/world_tile_map_generate` calls vanilla
`GetOrGenerateMapUtility.GetOrGenerateMap`, and `Base_Player` and
`Base_Faction` both contain the `MutatorPostTerrain` genstep (read from 1.6
source). The bug is in **def loading**, upstream of every map: a normal
player landing on any river, lake or coastal tile gets no water, fishing has
nothing to fish in, and any save holding existing water terrain would fail to
resolve it. This is maximally serious and is not a debug-path quirk.

## what was done, and what is still owed

**Done (repo only — nothing deployed, game untouched):**
- Corrected all 37 lowercase `<viscosityClass>` values to the enum's real
  casing across 14 files (13 `Defs/LiquidTypes/TerrainDefs/RM_*.xml` plus the
  compat patch). All 48 sites now read `Thin`/`Water`/`Thick`/`Heavy`.
- `generate_liquid_suite.py` gained `_enum_xv()`, used by all three emitters:
  it case-corrects a known enum field and **raises** on a value the enum does
  not have, so a regeneration cannot silently reintroduce this.
- `src/RimMandrake/bridgetools/prove_river_water.py` is the repro and the
  fix-verification: check A reads whether the nine defs exist (with six
  untargeted control defs that must stay present, or the run is declared an
  instrument failure); check B (`--generate`) generates a map, censuses every
  cell, and removes what it made.

🔴 **OWED, and deliberately NOT done without the owner: deploy + live verify.**
The fix only reaches the game through `deploy_custom_mods.py --apply` and a
cold load, which ends his current session. The verification after that is one
command: `python.exe src\RimMandrake\bridgetools\prove_river_water.py`
(expect `FIXED — water defs load`), then `--generate` for a map-level check.

⚠️ Also owed, same cause, not investigated here: FlowWorks' **own** liquid
terrains (`RM_Ooze`, `RM_Ammonia`, `RM_AcidWater`, `RM_Ichor`, `RM_Propane`,
`RM_Tar`, `RM_Coolant`, `RM_FuelSap`, `RM_ReactionLiquor`,
`RM_WaterBrackish`, `RM_WaterBrine`, `RM_WaterFrigid`, `RM_WaterMineral`)
carried the same lowercase values in their own def files, so they were being
discarded too — FlowWorks has very likely never had working liquids in game.
Worth a look once the fix is live.

⚠️ Independent of this bug, three mod gensteps NRE on every map generation and
should be triaged separately: `MineralsFramework.GenStep_MineralsFramework_Rocks`,
`GeologicalLandforms.BiomeGrid.UpdateOpenGroundFraction` (via
`GenStep_Animals` and again in `FinalizeInit`), and
`MapPreview.Patches.Patch_RimWorld_TerrainPatchMaker.GetHashCode` inside
`GenStep_Terrain`.

## verify
- **PROVE**: `python.exe src\RimMandrake\bridgetools\prove_river_water.py`
  against a live bridge.
- **EXPECT**: all nine patched defs `FOUND`, and `--generate` showing
  water-family terrain on a river/lake/coast tile.
- **LIES**: a screenshot settles nothing — a generated map has rendered as a
  blank mesh while holding correct data. Read the DATA. And a full-map
  terrain census must confirm `cellsRead == sizeX*sizeZ` before its "no
  water" is a result rather than a coverage gap; the first pass of this
  investigation reported `ZERO WATER` off a mis-named result field and was a
  query bug, not a measurement.
- **THRESHOLD**: the six control defs must stay `FOUND` in any run — if they
  go missing the instrument is broken, not the game.
