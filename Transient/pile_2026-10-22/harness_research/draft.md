# Agent harnesses for RimMandrake — draft for review (2026-10-22)

All web sources were seen on 2026-10-22. "Primary" = vendor page/docs/paper; "secondary" = blog/aggregator.
Our-setup facts are in `setup.md` (attached).

## The answer in five lines
1. No product on the market can drive our live game for us out of the box: every hosted coding agent (Devin, Codex cloud, Jules, Copilot coding agent, Cursor cloud agents, Claude Code cloud sessions) runs in a remote Linux sandbox, while our test rig is one Windows game process with one bridge, driven by one agent at a time.
2. The independent evidence for "autonomous AI engineer" products on messy, convention-heavy repos is weak (Answer.AI: 3 successes in 20 Devin tasks; METR RCT: experienced devs 19% slower with AI while believing they were 20% faster). Our repo is about as convention-heavy as they come.
3. Our measured bottlenecks are not "agent capability". They are: a serial live resource, collisions from sharing one clone, an LLM orchestrator that sleeps between notifications, and the owner's attention for loose design.
4. So the best moves are (R1) turn the live proof belt into a deterministic machine and try a second game lane; (R2) give every writer its own clone and land through a serial lander, and pilot a cloud agent only on offline items; (R3) make owner decisions default-proceed and asynchronous so no slot waits on him.
5. Each comes with experiments of a day or less and a pass/fail bar. Run those before buying anything.

**The pattern:** cloud agents fit the *offline* half of our work (XML, Python selftests, C# compiled against reference DLLs) and the *issue-tracker/phone* channel. None of them fits the live half without running on Archmagi itself, and once they do, they are just another driver competing for the one bridge.

## Three recommendations

### R1 — Make the live proof belt a machine, not an agent, and test a second game lane
**What changes:** a deterministic Python "belt runner" (no LLM in the loop) watches origin/main for FlowWorks DLL commits, runs the plan, takes the game down, deploys, relaunches through Steam, runs the queued proof scripts, and writes result JSON plus a one-line ledger note. An LLM is woken **only** on a FAIL, to classify it as MOD, SITE or HARNESS. Separately, we test whether a second RimWorld instance (its own `-savedatafolder`, its own `GABP_SERVER_PORT`; our client already reads that variable, `src/RimMandrake/Utils/rimbridge_client.py:84`) can run beside the first.
**Expected gain:** today's belt spent its idle gaps (16-28 min, MEASURED) waiting on an LLM turn. A machine re-proves as soon as a fix lands, and runs overnight. A second lane would double live throughput if RAM and Steam allow it.
**Costs/risks:** building the runner takes 1-2 days. The runner must respect the BRIDGE lock and "never leave a broken game running". A second instance may be refused by Steam or DRM, the memory says "launch via Steam, not bare exe", and the full mod list needs a lot of RAM. HARNESS FAILs still need judgment.
**Compatibility:** native. It drives rimbridge exactly as the proof scripts do now. No design ambiguity enters it.
**Experiments:**
- E1.1 (half a day): replay today's proof list through a dumb runner script on the minimal list overnight. PASS if it completes ≥ 80% of today's scripts unattended with no stranded game state. FAIL if any run leaves the game in an error storm.
- E1.2 (2 h): launch a second RimWorld on the 13-mod minimal list with `-savedatafolder=<alt>` and `GABP_SERVER_PORT=<alt>`. PASS if both bridges answer `rimbridge/ping` and one proof runs on each at the same time. Record peak RAM.

### R2 — One clone per writer and a serial lander; pilot a cloud agent only on offline items
**What changes:** stop sharing a working tree between writing helpers. Each writer gets its own ext4 clone (as BENCH and FOUNDRY already have; this is not a git worktree, so the worktree ruling is respected in letter. The owner should still rule on it). Writers push to `helper/<item>` branches. One lander (a script) rebases or merges them onto main one at a time and runs `run_selftests.py --only` and the pre-push lint. In parallel, pilot one hosted agent (Claude Code cloud session or Codex cloud, both reachable today) on 3-5 **offline-only** items (XML defs, Python selftests, docs), where a fresh sandbox and a PR are an advantage.
**Expected gain:** this removes today's `publish REFUSED` class (2 refusals, 11 stranded commits, MEASURED in belt.md) and the "one writer at a time when paths could overlap" serialisation. The cloud pilot tells us whether offline work can leave the machine entirely.
**Costs/risks:** disk, plus a clone sync step (minutes on ext4). DLL `.srchash` pairs and ledger shards need lander rules. Cloud agents lack our skills/hooks unless they are committed, can't build against the RimWorld DLLs unless reference assemblies are provided (a licence question), and may ignore conventions (the Answer.AI failure mode).
**Compatibility:** good. Live testing is untouched, and helpers still hand off to the belt.
**Experiments:**
- E2.1 (1 day): run one day with 3 helper clones and the lander. PASS if there are 0 publish refusals and 0 lost commits, and lander latency is under 10 min per branch.
- E2.2 (1 day): give 5 closed-spec offline items to a cloud agent (with the same prompt as a local helper). PASS if ≥ 3 of 5 PRs merge with ≤ 1 review round and pass `code_review_status` and selftests. Compare the token/$ cost against local helpers.

### R3 — Default-proceed decisions and a heartbeat orchestrator
**What changes:** (a) every question card carries a recommended option plus a deadline. If the owner hasn't answered by then, the recommended option executes, logged as `--by-card "<default, unanswered>"` with a one-tap undo. Taste calls (art, his north-star bars) stay hard-blocking. (b) A heartbeat, a local scheduled task or the existing systemd-timer pattern, wakes every 20-30 min. It checks slot occupancy, bridge state and failed runs, and refills slots from `rimflow next`, so slots never sit idle waiting for an orchestrator turn. (c) Owner contact moves to a phone-first surface we already have (Remote Control / Claude Projects threads on this computer). One digest goes out per window, not per event.
**Expected gain:** the owner's time goes only to taste and irreversible calls. Today's helper slots, idle for long periods (seat's report), are refilled within 30 min.
**Costs/risks:** a default can be wrong. That cost is bounded by making defaults reversible and excluding cosmetic changes (which need his permission by standing rule). Heartbeats burn tokens. RC fragility is documented (`/login` kills RC everywhere).
**Compatibility:** good. It works around loose design by asking less and asking better, and it does not touch the bridge.
**Experiments:**
- E3.1 (1 day): run a shadow day. Log every card we would have sent with its default, then have the owner mark at day's end which defaults he would have overturned. PASS if ≤ 1 in 10 is overturned.
- E3.2 (1 day): run the heartbeat for one belt day. PASS if no slot sits idle for more than 30 min while `rimflow next` has eligible items (measured from the ledger), at ≤ N tokens/hour.

## What we would NOT do
- Buy Devin/Factory/Jules seats to "run the project". They can't reach the game, and the independent evidence is weak.
- Adopt a worktree-based multi-agent manager. Worktrees are OFF by ruling, and none of them knows about the bridge.
- Turn on agent teams for live work. It is experimental, doesn't work with `-p`, and the docs warn that same-file edits lead to overwrites.
