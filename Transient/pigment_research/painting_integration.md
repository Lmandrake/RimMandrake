# Deepfire (mandrake.rm.luminouspigment) — painting integration research

2026-09-25. Engine facts read from the decompiled 1.6 source via RimSage. Builds on `engine_feasibility.md` (same folder). Every claim marked MEASURED (with class/method or file) or UNMEASURED.

**TL;DR.** Core = a separate Deepfire designator/job + `CompDeepfire` on items + one `MapComponent` owning proxy `CompGlower` lights (buildings, floor cells, pawns alike), colour read live from `thing.DrawColor` / floor colour grids and refreshed by the engine's own `Notify_ColorChanged` fan-out. That works on every vanilla path and every live colour mod except Dub's Paint Shop floors, which need a soft reflection read. Combat: postfix `ShotReport.HitReportFor` (Yayo-compatible) + a `StatPart` on `MeleeDodgeChance`.

## 3. Fallback: standalone Deepfire designator reading colour from whatever set it

**Verdict: TRUE — this should be the core, not the fallback. A separate "Deepfire" designator + job (costing the Deepfire pigment, not Dye) that marks a Thing or floor cell as luminous, with the colour READ at light-time from `thing.DrawColor` (and for floors `TerrainGrid.ColorAt(c)` → DPS grid), works across every path in §1 and every live mod in §2 with no patches on any colour UI. Per-UI toggles become optional sugar.**

Why it covers everything (MEASURED):
- `thing.DrawColor` resolves Building paint → `CompColorable` (vanilla dye, Character Editor, Self Dyeing, DPS, Craft with Color) → comp `ForceColor()` (Odyssey `CompUniqueWeapon`) → stuff/graphic colour (§1 table).
- Re-colouring after Deepfire is applied: every Thing path calls `Notify_ColorChanged`, which `ThingWithComps` forwards to every comp — so a `CompDeepfire.Notify_ColorChanged()` re-reads `DrawColor` and updates its light. No Harmony. Floors: postfix `TerrainGrid.SetTerrainColor` + terrain-change hook (§6); DPS floors: poll/reflect `MapComponent_PaintShop` (its own `SetColour`, soft patch).
- Worn apparel/weapons: `Apparel.Notify_ColorChanged` also dirties the wearer's graphics (`Apparel.cs` l.202); our comp sees the same call.

Recommended architecture:
1. **`CompDeepfire`** (ThingComp) injected at startup (code, like DPS's `PaintableDefsInit`) into every ThingDef that is a `ThingWithComps` AND (`building.paintable` || `IsApparel` || `IsWeapon` || has `CompColorable` || has `CompArt`). State Scribed on the comp: `int applications`, `bool qualityBumped`. Survives minify/haul/equip because it is on the item.
   - First application: art item (`CompArt` present) → `CompQuality.SetQuality(q+1, ArtGenerationContext.Colony)` once (engine_feasibility.md §2, incl. the art-title trap); non-art → a `StatPart` on `Beauty` reading `applications>0` (XML patch on `StatDef[defName="Beauty"]/parts`). Further applications raise brightness/radius only.
   - `Notify_ColorChanged` / `PostSpawnSetup` / `PostDeSpawn` / `ThingComp.Notify_Equipped(Pawn)`/`Notify_Unequipped(Pawn)` (MEASURED `ThingComp.cs` l.186-190; `Pawn_ApparelTracker` calls `apparel.Notify_Equipped/Unequipped` at l.781/799, so this covers apparel as well as weapons — forwarding to comps via `ThingWithComps` assumed, UNMEASURED) / `Notify_WearerDied` tell the manager to (re)light, move to wearer, or douse.
2. **`MapComponent_DeepfireLights`** owns ALL Deepfire lights as **proxy glowers**: an unspawned `ThingWithComps` of a tiny `RM_DeepfireLight` ThingDef carrying a `CompGlower` subclass that overrides the virtual `GlowColor`/`GlowRadius` (MEASURED virtual in `CompGlower`). Registered with `map.glowGrid.RegisterGlower` directly; re-registered via `ForceRegister` on colour/brightness/position change; rebuilt from comps + floor grid on load (glowers are never saved — MEASURED `GlowGrid` holds them only in `litGlowers`).
   - **Why a proxy and not a CompGlower on the painted thing:** lamps already carry a `CompGlower`, and `GlowGrid.GetGlowerIndex` finds a light by `parent.thingIDNumber` (MEASURED) — two glowers on one parent would share an id and `DeRegisterGlower` could remove the wrong one. Also `CompGlower.ShouldBeLitNow` is false for unspawned parents, so a glower on worn apparel never lights (engine_feasibility.md §1). One proxy type covers buildings, items on the ground, floors and pawns.
   - Unspawned proxy is UNMEASURED in game (engine reads only `Position`, `thingIDNumber`, `def.plant`, props — none require Spawned). Quicktest it first; fallback = a real spawned invisible Thing (GravTide/Rikiki pattern).
3. **Brightness**: glow intensity is the colour's magnitude — `GroundGlowAt` = max(r,g,b)/255 × 3.6, capped 0.5 unless overlit (MEASURED). "Dim" = scale the dye colour down. To make the pawn light "drive off darkness" psychologically it must exceed `GameGlowLitThreshold` 0.3 at the pawn's cell → max channel ≳ 21/255 at the centre; a very dark dye (e.g. deep blue at low value) might never qualify — normalise hue to a minimum value.
4. **Designator + job**: `Designator_Deepfire` (things + cells, like DPS's "paint all" tool) → `WorkGiver`/`JobDriver_ApplyDeepfire` consuming the pigment item (no Dye hard-coding to fight). For worn items, a styling-station-style job or "apply to item on the ground" only.
5. Optional sugar later: a "Deepfire" `FloatMenuGridOption` in `Designator_Paint.ProcessInput`, a checkbox in `Dialog_StylingStation.DrawApparelColor` — both just queue the same Deepfire job.


## 4. Moving pawn light — precedent and cost

**Verdict: no vanilla precedent (MEASURED: `GlowGrid.RegisterGlower/DeRegisterGlower` are called only from `CompGlower` itself — `CompGlower.cs` l.107-147, l.361-366; `GlowLight` snapshots `parent.Position` at registration). Two mod precedents, both "a separate light Thing that follows the pawn"; one of them is LIVE in our list. Recommended: one glow-proxy per glowing pawn, re-registered only when the pawn's cell changes, radius ≤ 2.5.**

Precedents:
- **Rikiki "MiningCo. MiningHelmet"** (source github.com/Rikiki123456789/Rimworld, `ApparelWithMiningLight.cs`, MEASURED by reading it): an `Apparel` subclass whose `Tick` (throttled to once per `GenTicks.TicksPerRealSecond` while off) computes `Wearer.DrawPos.ToIntVec3()`; if it differs from `light.Position` it **`Destroy()`s the old light Thing and `GenSpawn.Spawn`s a new `MiningLight` ThingDef (a CompGlower carrier) at the new cell**; the light is Scribed as a reference. Only lit when roofed & `PsychGlowAt <= Lit`, or unroofed & `< Overlit`. **Belt Flashlight** (Workshop 3403230282, 4,046 subs) says it is built on this code; **Safety Helmet with Light** (2073947744, 1,898 subs) credits Rikiki too — its page comments report moving-light lag (from web search summary, UNMEASURED directly). **Handy Lantern** (2808047855, 18,950 subs) and **Good Lighting** (3525571252, 2,070 subs; drafted "tactical flashlights") — method UNMEASURED (no public source found; Steam pages 429'd). None of these four is in our live list.
- **GravTide** (`gravtide.mod`, Workshop 3779600989, author yongdd, **LIVE**): has `ApparelLightExtension` (`glowRadius`, `glowColor`, `underwaterOnly`) and `MapComponent_WornLights` (fields `nodeDef, lights, stale, seen, lit, moved, made, doused`; methods `LampWorn, Brightest, Light, Rebind, Follow, Extinguish, Douse, Sweep`, driven from `MapComponentTick`). Its member references include `GenSpawn.Spawn`, `Thing.set_Position`/`SetPositionDirect`, `CompGlower.ForceRegister`, `set_GlowRadius`, `set_GlowColor` (MEASURED with dnfile metadata dump of `GravTide.dll`). So it keeps a spawned node Thing per lit pawn and moves it (inference from names + refs; the IL was not decompiled — UNMEASURED which of Spawn-per-move vs move+ForceRegister it uses). **This is the most important compatibility fact for Deepfire: a live mod already manages worn-apparel lights via a map component; Deepfire's pawn light should be tested alongside it, and could even reuse its pattern.**
- Anything patching `GlowGrid` directly to support movers: none found (MEASURED scan of every live mod DLL's type names for Glow/Light/Lamp/Torch/Lantern; noise excluded). GravTide patches `GlowGrid.Register/DeRegister` postfix only for its underwater lights.

Cost per move (MEASURED shape from `GlowGrid`):
- `DeRegisterGlower`: linear `GetGlowerIndex` over all lights + `lights.RemoveAt`; `DirtyCell` on every cell of the old `AffectedRect` — each `DirtyCell` also calls `map.mapDrawer.MapMeshDirty(cell, Roofs)` and `(cell, GroundGlow)` and `map.events.Notify_GlowChanged(cell)`. `RegisterGlower` does the same for the new rect.
- Next frame `GlowGridUpdate_First`: `ComputeGlowGridsJob` over all lights (only `dirty` ones flood-fill; the moved light's flood is ~diameter² cells), then `CombineColorsJob` over all grid cells, where each dirty cell loops **every** light's rect test. Plus section-mesh regeneration of the Roofs and GroundGlow layers for the 1–4 17×17 sections touched.
- For radius 2.5 (diameter 6 → 36 cells, ×2 rects) this is small per move; a pawn walking crosses a cell every ~10–25 ticks. Ten glowing pawns walking = roughly one light re-register per tick on average. Per-frame ms UNMEASURED — needs a profiler run (Dubs Performance Analyzer) on the Desktop.
- **Cheaper than Rikiki**: do not spawn/destroy a Thing per step (that adds `GenSpawn` + map-mesh Things dirtying + ID churn); keep ONE proxy per pawn and on cell change do `proxy.Position = newCell` (unspawned proxy: plain field write; spawned: `SetPositionDirect` + thingGrid bookkeeping) then `glower.ForceRegister(map)`. Throttle checks with `CompTickInterval`/`TickRare`, update only on cell change, only while `!pawn.Position.Roofed || dark`, and skip when the pawn is not spawned (caravans, carried).
- Design consequence (MEASURED, §5): a lit pawn makes `PsychGlowAt(pawn.Position)` non-Dark, so the pawn itself no longer counts as "in darkness" for Ideology darkness precepts, Anomaly `Hediff_LightExposure`, `ThoughtWorker_SwallowedByDarkness`, and `SilhouetteUtility` hiding. That is thematically what "drives off darkness" means — confirm with the owner.


## 5. Darkness and combat in 1.6

**Verdict: vanilla light affects hit chance ONLY through Ideology precept stat offsets on the attacker, and the "dark" test for outdoors uses SKY glow only — so a pawn's own light cannot flip an outdoor target to "lit" in vanilla. Cleanest hook for "easier to hit when glowing in the dark": a Harmony postfix on `ShotReport.HitReportFor` (ranged) plus a `StatPart` on `MeleeDodgeChance` (melee, target-side stat, no Harmony).**

- MEASURED `ShotReport.HitReportFor` (`Verse/ShotReport.cs` ~l.139-160): `offsetFromDarkness` = the CASTER's `ShootingAccuracy{Outdoors,Indoors}{Lit,Dark}Offset` stat, only `if (ModsConfig.IdeologyActive && target.HasThing)`, category chosen by `DarknessCombatUtility` on the TARGET. It is additive in `AimOnTargetChance_StandardTarget` (`factorShooterAndDist × equipment × weather × gas × execution + offsetFromDarkness`, floor 0.0201). Non-zero only when an ideo precept carries those stats.
- MEASURED `DarknessCombatUtility` (`Source/Global/DarknessCombatUtility.cs`): *Outdoors* = room `PsychologicallyOutdoors` and not under natural/thick roof; outdoor dark/lit is **`map.skyManager.CurSkyGlow > 0.35`** only — ground glow ignored. *Indoors* dark = `PsychGlowAt(pos) == Dark` or `DarklightUtility.IsDarklightAt`. So a Deepfire light around the target **indoors** would turn "IndoorsAndDark" into "IndoorsAndLit" (a darkness-ideo shooter would then use its Lit offset); **outdoors it changes nothing**.
- MEASURED melee: `Verb_MeleeAttack.GetNonMissChance` (caster `MeleeHitChance` + the same four precept offsets) and `GetDodgeChance` (TARGET's `MeleeDodgeChance` stat + target's dodge offsets). Both Ideology-gated.
- MEASURED other darkness mechanics (none touch hit chance): Anomaly `GameCondition_UnnaturalDarkness` (GroundGlowAt ≤ 0 cells), `ThoughtWorker_SwallowedByDarkness`, `SilhouetteUtility` (hides non-player pawns when `MapBrightness < 0.1` and `GroundGlowAt <= 0` — a Deepfire light would un-hide a hostile under unnatural darkness), `CellFinderLoose` noctol spawn avoidance (`PsychGlowAt == Dark`), `CompSightstealer` (visibility scales with GroundGlowAt), `StatPart_Glow` (caster work/stat factors). No `ShotReport` factor from Anomaly or Odyssey (search of ShotReport shows only Ideology offsets).
- MEASURED: `Hediff_LightExposure`, `PawnRecentMemory` (last-lit tick) and `ThoughtWorker_Precept_IndoorLight` read `PsychGlowAt(pawn.Position)` — a pawn carrying light will count as "in light" for Ideology darkness/light precepts and Anomaly light-exposure. A design consequence worth stating to the owner.

**Recommended hook (design):**
- Ranged: `[HarmonyPostfix] ShotReport.HitReportFor(Thing caster, Verb verb, LocalTargetInfo target, ref ShotReport __result)` — if target is a Pawn with an active Deepfire personal glow AND the *surroundings* are dark (compute our own test: sky glow ≤ 0.35 or GroundGlowAt WITHOUT our light — we know our own contribution), multiply the private `factorFromTargetSize` (via `AccessTools.FieldRefAccess<ShotReport,float>`) by e.g. 1.25, clamped to vanilla's 0.5–2 range. It then appears in the vanilla readout as "Target size" with no readout patch; for a labelled line, postfix `GetTextReadout`. Works with no DLC.
- Melee: a `StatPart` subclass added to `MeleeDodgeChance` by XML patch (`StatDef.parts`), returning a negative offset when the pawn glows in the dark. Shows in the stat explanation automatically.
- MEASURED **Yayo's Combat 3 (LIVE)** replaces `Verb_LaunchProjectile.TryCastShot` with a prefix returning false, but still calls `ShotReport.HitReportFor(...)` and rolls on `AimOnTargetChance_IgnoringPosture` (its `Verb_LaunchProjectile_TryCastShot.cs` ~l.139-143; source github.com/emipa606/YayosCombat3). `AimOnTargetChance_IgnoringPosture` includes `factorFromTargetSize`, so the HitReportFor postfix stays effective under Yayo. Its `ShotReport_HitFactorFromShooter` postfix only touches the shooter factor — no conflict.
- Combat Extended: not in the live list (MEASURED, ModsConfig parse); CE replaces ShotReport entirely — out of scope.


## 6. Floors — can a painted floor cell glow?

**Verdict: YES, but not through terrain glow. Terrain glow is per-TerrainDef (one colour for every cell of that def), so a per-cell tinted floor light must be a comp-glower owned by a map component. Recommended: an unspawned proxy `ThingWithComps` + `CompGlower` per lit cell (or per cluster), registered directly with `GlowGrid.RegisterGlower`.**

- MEASURED `GlowLight(IntVec3 cell, Map, int)` (`Verse/Glow/GlowLight.cs`) reads `TerrainDef.glowRadius` / `glowColor` from `terrainGrid.TerrainAt(cell)` — colour is the DEF's, not the cell's. `GlowGrid.RegisterTerrain` is called only from `TerrainGrid` setters when `glowRadius > 0`. A "Deepfire floor" TerrainDef per colour would be N×(every floor) defs and would lose the floor type — rejected.
- MEASURED `GlowGrid.RegisterGlower(CompGlower)` takes any `CompGlower`; `GlowLight(CompGlower,…)` reads only `Props.overlightRadius`, `GlowRadius`, `GlowColor`, `parent.def.plant`, `parent.thingIDNumber`, **`parent.Position`**. It never checks `Spawned`. So a map component can hold unspawned proxy things (given an id via `ThingIDMaker.GiveIDTo`, `Position` set) and register their glowers directly. (The `Spawned` check is only in `CompGlower.ShouldBeLitNow`/`UpdateLit`, which we would not call.) Proxy approach UNMEASURED in game — needs a quicktest; the alternative with zero engine risk is a real spawned invisible 1×1 Thing (`drawerType None`, `selectable false`, `useHitPoints false`, `altitudeLayer Floor`, not blocking) per lit cell, as floor-light mods do (see §4).
- MEASURED floor-paint state to read colour from: vanilla `TerrainGrid.colorGrid[i]` (`ColorAt(c)`), and — for Dub's Paint Shop — its own `MapComponent_PaintShop` R/G/B/A grids (`GetColour`), not colorGrid (§2).
- MEASURED lifecycle traps: every terrain replacement nulls `colorGrid` (TerrainGrid l.248/306/368/425), without calling `SetTerrainColor`.
