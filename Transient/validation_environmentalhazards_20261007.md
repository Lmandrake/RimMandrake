# EnvironmentalHazards validation 2026-10-07

## 1. Survey (invariant value per extraction cost)
Picked:
1. **Salinity axis shift + surge** (`RM_MapComponent_GradientAxis` + `RM_GameCondition_GradientSurge`). Long-horizon state machine (a shift is a proportional slice every 250 ticks over days, a recede continues after its condition is gone, per-cell clamp, ushort save quantisation) that a live chain cannot cover: needs many surge/recede cycles and saves. Extraction ~12 one-line expressions.
2. **Stranding pools grid logic** (`RM_MapComponent_StrandingPools`). Flood-fill labelling, main-network pick, pool continuity across recede events, bounded reconnect fill, decay target, shoreline-first removal. Pure grid maths with real edge cases (cells[0] no longer water, ties, shared cells). Extraction ~150 lines, the best oracle-checkable code in the mod.
Not picked, and why:
- `HediffComp_PeriodicAreaAttack`: timer is 6 lines (`ticksUntilBurst -= delta`); the rest is Verse-bound damage dispatch. Its one real edge (a large coalesced `delta` fires one burst and drops the overshoot) is a design choice, not a sequence bug.
- `RM_GameCondition_WeatherPulse` (burst/MTB/scald cadence): good state machine but ~70% engine calls (weather snap, flash cycle, MapComponent), and the Forge cycle subclass overrides its seams; extraction would touch two files for 3 invariants.
- Exposure/protection (`ProtectionDriveFactor`, `SeverityChangePerDay`, SunlightScald): stateless 2-line clamps; a property test, not a sequence fuzz. Cheap to add later.
- `WaterAgitation`, `TreeFallUtility`, `WetBulb` ramp: dominated by Rand/Fleck/Map calls with no state worth sequencing.
- `LivingRegrowth`, `SumpLivingMap`, `DreadField`: large, Scribe-heavy, Map-bound; a kernel would be a rewrite, not an extraction.

## 2. Kernels + fuzz
- **Files**: new `Source/RM_AxisKernel.cs`, `Source/RM_PoolKernel.cs` (Verse-free; csproj +2 `Compile` lines); call sites in `RM_MapComponent_GradientAxis.cs`, `RM_GameCondition_GradientSurge.cs`, `RM_MapComponent_StrandingPools.cs` now call them (same float op order, same BFS/direction order, Scribe names unchanged: shiftInProgress, shiftDeltaRemaining, shiftTicksRemaining, shiftIsRecede, lastRecedeCompletedTick, updateCooldown, salinity; pools, nextPoolId, lastSeenRecedeTick, updateCooldown). Wrapper `src/RimMandrake/Utils/selftest_envhazards_fuzz.py` (found by run_selftests.py).
- **Behaviour preservation** is by construction, not game-proven. One assumption not checked against the decompile: `Map.AllCells` walks z-major so scan order == index order (only the order of components and their tie-break would differ, never the partition). The StrandingPools call site now converts IntVec3 lists to index lists on each reconcile pass (allocation per pool per 250 ticks, negligible).
- **Invariants (axis)**: salinity in [0,1] always and monotone with the slice sign; every slice has the shift's sign, is <= what remained and equals the constant-rate share D*step/T (telescopes); step in [1,min(250,remaining)]; a clean shift of T ticks takes exactly ceil(T/250) updates and applies D within 1e-4; lastRecede set only at a finishing recede and never in the future; TotalDelta in [0, front/mapsize]; recede in [-total,0] and total+recede == total*residual; a clean forward+recede cycle lands unclamped cells exactly on start + total*residual; save->load error <= half a quantum, reload stays in [0,1]; all 65,536 stored ushort values reload and re-save unchanged; quantisation monotone; the two salt-line band spellings agree away from the float edge.
- **Invariants (pool)**: components partition the water exactly (vs an independent labelling), each starts at its lowest cell, in scan order; main is the first largest; MatchPools == brute force (first owned cell, later pool owns shared cells, main never matched); Reconnected == full-reach oracle (edge or > cap) incl. start cell not water; PickEdgeIndex == first shoreline cell else last; decay target in [0,original], non-increasing in time, 0 at/after the end, no-op conditions exact; registry: ids unique/ascending, no duplicate or out-of-grid cells, pools never grow between detect passes, after a pass every pool is at/under its target, any pool past its decay window is gone, removed cells are shoreline-first.
- **Seeds**: default (axis 4,000 + quant 265,536 + prim 20,000 + pool 5,000, seeds 1..N) 1.5M + 3.6M + 0.19M steps, ~13 s: 0 failures. `--fuzz-scale 10`: axis 40,000 seq (~15M steps), quant 2.1M, prim 200,000 (36M steps), pool 50,000 (1.9M steps): 0 failures, ~2 min.
- **Mutation** (each restored, diff clean; 4 s sleep+touch between builds per the Hum trap):
  - StepDelta `/ (ticksRemaining + 1)` -> `axis seed 1: slice ... is not the constant-rate share | Surge EndSurge Update(4)`
  - Reconnected edge `width - 1` -> `width - 2` -> `prim seed 4: Reconnected=True ... disagrees with oracle`
  - PickEdgeIndex fallback `Count - 1` -> `0` -> `prim seed 116: PickEdgeIndex 0, oracle 1`
  - Quantize Round -> Floor -> `quant: 0.771 -> 50533 -> 0.77108 beyond half a quantum`
  - MainIndex `>` -> `>=` -> `prim seed 40: main is not the first largest`
  - decay target +1 -> `prim seed 8: target 3 outside [0,2]`
  - Apply clamp upper only -> `axis seed 1: cell 0 salinity -0.37 left [0,1]`
  - decay floor 20% -> `pool seed 2: pool 5 survived past its decay window | Detect Tick Tick` (pool sequence family)
- **Observations (not failures, harness-level; the real component also runs these paths)**:
  - A new `ShiftAxis` while one runs discards the remainder (23,647x in 4,000 sequences; 8,178 of them cut a recede short, so `lastRecedeCompletedTick` never advances and the stranding pools never arm for that surge). The component's own random roll only fires when no shift runs (`TickSurgeRoll` is the `else` branch), so this needs a surge started another way (debug/storyteller). Worth deciding whether a second surge during recede should queue or add.
  - Per-cell clamp makes a surge cycle non-invertible for saturated cells (4,237 cell-cycles clamped): the "residual drift" promise only holds for unsaturated cells.
  - Pool continuity is lossy when pools merge or split (shared cells go to the later pool): 10k steps with overlapping tracked pools, 3.6k components left without a pool whose cells equal them, 10k pools fragmented by decay (shoreline-first can cut a 1-cell bridge). All benign until a pool's occupants matter: the stale/overlapping pool keeps decaying and repainting cells another pool owns.
  - Ghost pools (decayed cells that stay wet being re-registered as a fresh pool with a full timer) only occur when `dryTerrain` is null; shipped `RM_Miasma.xml` sets `dryTerrain`, so config-dependent.
