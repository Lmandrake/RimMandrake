## 2. Detectability: red and amber

- **RED / OOM: yes, already measured.** memwatch reads cgroup `memory.events`. One gap is that harness kills are not toasted.
- **RED / terminal stopped: yes.** A `claude-seat-*` scope that was active and is now gone, or a session file whose PID is dead or has a different `procStart`, means the window died. Telling a clean `/exit` apart from a crash needs the `SessionEnd` hook's `reason`. An API-error stop has its own `StopFailure` hook.
- **AMBER / waiting on a question card: yes, from two independent sources.** (a) Polling `~/.claude/sessions/*.json` for `status=="waiting"` together with `waitingFor`; Claude Code writes this itself for the peer and Remote Control roster. (b) A `Notification` hook (`permission_prompt`, `elicitation_dialog`, `idle_prompt`). UNMEASURED live: whether an `AskUserQuestion` card shows up as `waiting`/`dialog open` or as `idle`. That takes one 30-second test with a throwaway window. Even in the worst case, "finished its turn and idle for more than 60 s" (`idle_prompt`) is itself an amber state, because the window is waiting for him.
- **AMBER / stuck: inferable only.** `busy` with an old `statusUpdatedAt` and a transcript that has not grown for N minutes. This produces false positives on long builds, so it should show as dim amber and never flash.
- ⚠️ **Traps:** PID reuse (the 2 "AGENT VISION" files above); 34 session files on disk but only 6 live; the session-file format is internal to Claude Code and could change in any release, so the hook is the documented contract and the file is a convenience.

## 4. Three concepts

Mockups (full paths): `D:\Luke\dev\RimMandrake\Transient\away_dashboard_concept_A_2026-10-08.png`, `…_B_…png`, `…_C_…png`. HTML sources are in `Transient\away_dashboard_mockups_2026-10-08\`. The data shown in them is today's real ledger.

**Shared spine (all three need it, and it is the real work):** one small collector, `rimflow pulse`, run by an `rm-pulse.timer` every 15 s plus Notification/Stop/SessionEnd hooks. It joins the session files, seat scopes, memwatch events, ledger events, artpipe counts and bridge/game state into **one append-only `pulse.jsonl` plus a `pulse_now.json` snapshot**. Every line is `{key, kind: run|done|red|amber, who, text, since, link}`. A thing keeps its key, so a running line *becomes* its done line. The views are just renderers of that file.

### A · The Lantern (an always-on-top floating widget)
A small frameless window pinned to a screen corner. Alarms sit at the top and pulse until he acks them. Below them is one line per live thing, and finished work slides into "while you were away" with its links. **Lives:** Edge in `--app` mode against a localhost page served from WSL, made topmost by a tiny PowerShell call; or a WebView2 tray app. **Alarms:** a red block flashing for OOM or a dead window, an amber block for waiting. **Links:** each opens in Explorer through `show.sh`, or a native path. **Cost:** collector (about 1 day) plus a server and page (about 1 day) plus a Windows launcher/autostart (half a day, and fiddly). **Failure modes:** the server dies quietly in WSL; the window is closed and never reopened; topmost is lost after a game goes fullscreen; it has the most moving parts. **Why it might die:** it is FleetView with better data. It is pull, unless it autostarts and the alarms also push.

### B · The Return Ledger (a since-you-left page, published as an Artifact)
A morning paper written **when he comes back**. Saying "I'm back" (or a `UserPromptSubmit` hook spotting a gap of more than 30 min since his last prompt) regenerates one fixed-URL claude.ai Artifact: a two-sentence lede, BROKE, WAITING ON YOU (oldest first), FINISHED with links, STILL RUNNING. Ticks for "seen" are written back through the artifact database so the next edition omits them. **Lives:** a private Artifact that works the same on phone and desktop. **Alarms:** in the page only, with no realtime alerts, so it must be paired with a push for red. **Cost:** collector plus page (about 1.5 days). **Failure modes:** the links are `D:\` paths that a phone cannot open, so it needs GitHub links for anything committed; Artifact publish needs an approved session. **Why it might live:** nothing has to stay running, and it is generated at the exact moment it is needed.

### C · The Marquee (status-line strip, push alarms, and an on-command digest)
**No new window.** The Claude Code statusline he already watches gains a fleet strip (`✖ OOM 19:13 · ◐ BENCH 14m · ▶ FOUNDRY build · ▶ art 6/155 · ✓ 12 since you left`). Red and amber are **pushed** as a Windows toast (extending memwatch's toaster) and to the phone through ntfy. "I'm back" or `rimflow since` prints the one-line-per-thing digest with native paths. **Cost:** the lowest, about 1 day; the statusline is a Lodestar block that already exists. **Failure modes:** the statusline refreshes every 60 s and only while a window is open; toast fatigue if amber is noisy; it is not "beautiful" in the floating-glow sense. **Why it might live:** every piece is push or rides a surface that already survived.

## 5. GPT review: what it added and what we adopted

The full transcript is at `D:\Luke\dev\RimMandrake\Transient\away_dashboard_gpt_review_2026-10-08.md` (gpt-6.1-sol, high effort, text only, without the mockups).

**Adopted:**
- **Separate three things on every line:** work state, attention state, and *data freshness*. Stale data must never look healthy. The collector shows its own "last collected" stamp, and a stale view goes grey with a STALE badge.
- **Sharper alarm meanings.** Red is a confirmed OOM *kill*, an unexpected session loss, or a failure that stops work. Memory pressure is not red, and a clean `/exit` is neutral. Amber is an *explicit* unanswered request. "No observed progress" is dim amber and never flashes.
- **Motion rules.** A new incident blinks briefly and then holds a steady red. Activity breathes slowly. A reduced-motion switch is included. This keeps "beautiful" from turning into "exhausting".
- **Ack is not resolve, and snooze delays delivery, not visibility.** One incident ID is used across desktop and phone, so acking on one acks both.
- **A stronger spine:** versioned events carrying source cursors, process identity = host + boot ID + PID + start time (this fixes the PID-reuse trap measured above), one reducer that owns the writes, and hooks that only append to a spool and return immediately, so a broken monitor can never slow an agent down. The session-file parser sits behind a version adapter, and when parsing fails the view shows degraded coverage instead of guessing.
- **Who watches the watcher:** a Windows scheduled check confirms the snapshot is still advancing, and if it is not it raises exactly *one* "monitor down" alarm, not a flood of false "every window crashed" alarms.
- **Typed artifact links:** commit-pinned GitHub URL when the file is committed, local path otherwise, and a plain "desktop only" label on the phone instead of a dead `D:\` link.
- **A fourth concept, D · Attention Inbox:** a queue of *only* decisions and failures, delivered through Windows Notification Center and the phone, with all completions folded into a single "you're back" card. It has no ambient roster at all.
- **Its "don't build it" case** (section 6) and its **staged plan with a kill criterion** (section 8).

**Not adopted:**
- "Build A last" is kept as a recommendation, but it is the owner's call: A is the one he pictured.
- GPT counted *six* dead interfaces. That count includes FleetView's predecessor Cowork artifact, which is fair.

## 6. In plain words, for the owner

**What is possible.** Every Claude window already writes a small status file saying *busy*, *idle* or **waiting**, and when it is waiting it also says *why* ("input needed", "dialog open"). Claude Code also offers a documented "notification" hook that fires when a window needs permission or has sat idle for a minute, and nobody has switched it on yet. Memory kills are already caught every minute by memwatch. A window that dies leaves a trace: its process and its systemd scope vanish. **So red and amber are detectable today, with no guessing.** What is not yet proven: whether *a question card in particular* shows as "waiting" or merely "idle". That takes one 30-second test.

**What is not possible, or not honest.** "Stuck" cannot be known, only suspected: a 20-minute build and a hung tool look the same from outside. The phone cannot open `D:\` paths; it can only open things that are committed or published. And nothing tells us you are "away". We can infer it from a gap between your prompts, or you can say "I'm back".

**The history lesson.** Five or six dashboards died here, every one for the same reason: you had to go and open it, or an agent had to remember to refresh it. The three things that survived (memwatch toasts, the status line, and the Lodestar board) are each either **pushed to you** or **redrawn by a timer**. A beautiful widget will die the same way unless its alarms also push and its data refreshes itself.

**The honest "leave it" case.** Remote Control already lists every session and its state on your phone. The ledger already holds every outcome, and memwatch already toasts OOMs. The truly missing pieces may be small: toasts for harness OOM kills, an amber alert when a window waits on you, and a `rimflow since` command. Everything beyond that is polish, and it should be justified by the numbers below.

## 7. Metrics of value (measure a baseline first, mostly from logs we already have)

| Metric | Baseline, measured or how to measure | Target |
|---|---|---|
| **Returns per day** (context for everything below) | MEASURED: in the last 14 days, 833 typed prompts and **78 returns after a gap of 30 min or more, about 5.6 per day** (median gap 89 min), from `~/.claude/history.jsonl`. These are *candidate* returns, since a gap is not proof of absence. | — |
| **Time to notice a red event** (OOM kill or dead window → your next prompt to that seat) | Join memwatch `oom_kill` timestamps, and session-end times, to your next prompt. Today **5 harness OOM kills were never toasted at all.** | Median under 5 min while you are at the desk |
| **Age of an unanswered question** (window `waiting` → answered) | Not recorded today. A 15-s poller logging `status` transitions would give a baseline within a week, with no UI. | p90 under 15 min while you are home |
| **Minutes spent reconstructing state per return** | Sample 5 returns: time from your first prompt until your first *new* instruction, measured from transcript timestamps. | Halve it |
| **Finished-to-looked-at latency** (`implemented`/`close` event → you open its artifact or rule on it) | Join ledger close times to sheet-decision timestamps and `.decisions.json` mtimes. | Down 50% |
| **Pointers lost** (handoff pointers never picked up; the audit measured 25%) | Lodestar handoff audit, re-run. | Down |
| **Alert precision** (alerts you would call actionable) | Replay the proposed rules against a week of logs and label them. | 90% or better, or the alert type is cut |
| **Upkeep** (minutes per week spent keeping it alive) | Count restart and refresh prompts. | Under 15 min/week, or kill it |

**Kill criterion (from GPT, adopted):** after a two-week pilot, stop expanding if neither time-to-notice nor question age improves by 30%, if alert precision is below 90%, or if upkeep exceeds 15 minutes a week. Keep only the alerts and `since`.

## 8. Decisions (ready for question cards)

**Q1 · Build it at all?**
- **Leave it as it is.** Add only the one-line memwatch fix so harness OOM kills toast too. Zero upkeep, and Remote Control plus the ledger remain the view. *Trade:* you keep reconstructing state by asking.
- **Stage 1 only: alarms plus a digest.** Red and amber toasts plus `rimflow since`, all on the pulse spine, about 1–2 days. Each piece is useful alone. *Trade:* not yet the beautiful floating thing. **(Recommended: it attacks the measured gaps and matches the only pattern that has ever survived here.)**
- **The full beautiful dashboard now.** Spine plus the chosen surface, about 4–5 days. *Trade:* the highest risk of joining the dead GUIs before the alarms have proven themselves.

**Q2 · Where should the beautiful part live (after Stage 1)?**
- **A · Lantern**, a floating always-on-top widget. It is what you pictured. *Trade:* the most moving parts (Windows window plus WSL server plus autostart).
- **B · Return Ledger**, a morning-paper page at one fixed URL, readable on phone and desktop. *Trade:* not live; it needs a push to cover realtime red.
- **C · Marquee**, a fleet strip in the status line you already watch, plus toasts. *Trade:* beautiful only within terminal limits. **(Recommended first: it rides a surface that already survived, and A or B can be added on top of the same data later.)**
- **D · Attention Inbox**, only decisions and failures, in Windows notifications and on the phone. *Trade:* no "what's running now" picture.

**Q3 · What should turn amber?**
- **Only explicit requests:** a question card, a permission prompt, or "input needed". *Trade:* a window that silently stalls stays grey. **(Recommended: GPT's precision rule. False ambers are what get alarms switched off.)**
- **Also "finished and idle more than N minutes":** you see every window that is done and waiting for its next instruction. *Trade:* noisy; BENCH idles a lot.
- **Also suspected stuck:** busy with no progress for 20 min or more, shown dim. *Trade:* long builds will trip it.

**Q4 · Should alarms reach your phone?**
- **Desktop toasts only for now.** *Trade:* you miss red events while away from the desk.
- **Phone through ntfy (a private topic) after one week, if precision holds at 90% or better.** *Trade:* a third-party relay sees one-line alert text (it can be self-hosted). **(Recommended: the phone is where "while I was away" happens, but only after the alerts have earned it.)**
- **Rely on Remote Control's own session list.** *Trade:* no push at all; you have to look.

**Q5 · When does the "since you left" digest appear?**
- **When you say "I'm back"** (or run `rimflow since`). *Trade:* you have to remember to ask. **(Recommended first: a prompt gap is not proof that you were away.)**
- **Automatically on your first prompt after a gap of 30 min or more** (a hook prepends it). *Trade:* it fires when you were only reading.
- **At fixed times** (for example 07:00 and on return from work), published to the phone page. *Trade:* stale by the time you read it.

**Q6 · Measure first, or build first?**
- **Run a silent logger for a week first** (status transitions plus alert-rule replay), then decide on the numbers. *Trade:* a week of waiting.
- **Build Stage 1 and the logger together**, judging at two weeks against the kill criterion. *Trade:* no clean "before" for the ambers. **(Recommended: the red baseline already exists in memwatch, and the logger costs nothing.)**
