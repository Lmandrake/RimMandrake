# WeatherSuite — validation walk
subject: src/RimStarWars/WeatherSuite  (packageId `mandrake.rsw.weathersuite`, from About/About.xml)
deps: none (Ludeon.RimWorld only) — this is deliberately the generic engine half of WEATHER_SUITE_SLICE_1; the `PlanetGeometryDef` INSTANCE with Ash'karr's real substellar-point numbers is not shipped here, only the `PlanetGeometryDef` Def TYPE and the mechanism that reads it (About/About.xml, `Source/WeatherSuiteHook.cs` header)
list: minimal — and minimal is the interesting case: with no `PlanetGeometryDef` instance loaded (no RimUtinni wiring mod), the terminator/nightside geometry checks are proven-inert, not merely untested
status-hint: a fixed-geometry "arc from the substellar point" test any tidally-locked SW planet can reuse, driving a permanent terminator-front storm (vanilla `GameCondition_Flashstorm`, unmodified) and a nightside-gated maximized dark-side aurora (a small subclass of vanilla `GameCondition_Aurora`), plus a Tier-1 forecast-instrument building that reads the map's real weather-commonality table read-only (About/About.xml)

## must be true
- `WeatherGeometryUtility.ActiveGeometry` reads `DefDatabase<PlanetGeometryDef>.AllDefsListForReading.FirstOrDefault()` — on the minimal list (no `PlanetGeometryDef` instance anywhere) this is always `null`, so `TileInTerminatorBand`/`TileInNightsideBand` always return `false` and log the warning exactly once (`warnedMissing` static flag) the first time anything asks (`Source/WeatherSuiteHook.cs`).
- `MapComponent_TerminatorBand.FinalizeInit()` runs on every map and starts a **permanent** `RSW_WS_TerminatorFront` `GameCondition` only if `WeatherGeometryUtility.MapInTerminatorBand(map)` is true; on the minimal list that is never true, so no map ever gets the storm wall from this mechanism alone.
- `RSW_WS_TerminatorFront`'s `conditionClass` is vanilla's own `GameCondition_Flashstorm`, completely unmodified — the elevated-lightning payload is not this mod's code at all, only the "which maps get it, and forever" gate is.
- `RSW_WS_DarkAurora` is a SEPARATE `GameConditionDef` from vanilla's own `Aurora` (never touched) whose `conditionClass` is `GameCondition_DarkAuroraMax`, a subclass overriding only `SkyTarget()` to push sky saturation/brightness above vanilla's private `GameCondition_Aurora` constants; its paired `RSW_WS_DarkAurora` `IncidentDef` fires it via `IncidentWorker_NightsideAurora`, which requires `base.CanFireNowSub` true AND at least one player-home map in the geometry def's nightside band — on the minimal list that second condition is always false, so the incident never fires even though vanilla `Aurora` remains available and unmodified.
- `RSW_WS_DarkAurora`'s paired `ThoughtDef` reuses vanilla `ThoughtWorker_Aurora` unchanged (it reads its own def's `gameCondition` field rather than hardcoding vanilla's `Aurora`), granting `+14` mood to any pawn outdoors and not blind while the condition is active.
- `CompForecaster` (`RSW_WS_WeatherInstrument`'s comp) computes its own weather-commonality read on `CompInspectStringExtra()` (hover/selection only, never per-tick) via a read-only near-copy of `WeatherDecider.CurrentWeatherCommonality`'s public surface — it never touches `Rand`, so it structurally cannot desync the weather roll it reports on.
- The static-constructor log line `"[RimMandrake.StarWars.WeatherSuite] loaded — terminator-band and nightside-band geometry checks armed (MapComponent_TerminatorBand, IncidentWorker_NightsideAurora). No Harmony patches..."` fires exactly once per game process, from `WeatherSuiteHookMod`'s `[StaticConstructorOnStartup]` cctor.
