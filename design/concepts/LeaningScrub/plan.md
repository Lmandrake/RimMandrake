## Smother timing, settings and saves

Frozen scope says desiccation takes years; current source defaults to 30 days and computes every remaining time from the current global setting. Only `rmSmotherStartTick` is saved. These are verified product gaps, not an unanswered scope fork. Sources: `design/Jawa/worldbuilding/biomes/arid_shrubland.md:222`, `Defs/ThingDefs_Items/RM_SmotherCraft.xml:75`, `RM_LeaningScrubMod.cs:63`, `RM_SmotherCraft.cs:85`, `Kernel/RM_SmotherKernel.cs:10`. A 60-day engine year is corroborated by `CreatureBehaviors/Source/RM_WorldStarsMath.cs:13`.

Agent tuning selected for implementation: fresh configuration defaults to **120 days**, two engine years. Normal UI range **120–600 days**, displayed in days and years. These are tunable implementation numbers, not owner-picked values. Preserve the recipe's current 40 fiber + 15 felt to one blanket and 2400 work; one successfully completed 600-tick throw consumes one blanket. The claim remains a delayed banked resource; starting one does not certify an immediately harmless road. Keep the existing yield formula and exact stack splitting unless measured balance supplies a reason to tune them.

Snapshot a positive duration and due time for each new claim, plus a schema/version marker; use overflow-safe duration/due arithmetic. Later settings writes affect subsequent claims only. Saved active claims retain time owed, ownership and one payout. The same logic governs generated claims; at tick zero the current clamped start can be fresh, so the ruins description cannot claim an aged field the actual clock cannot represent.

| Imported state | Selected behavior |
| --- | --- |
| No old settings file/field | New configuration gets 120 days. |
| Existing serialized `smotherDays`, including old 30 or custom values below 120 | Preserve it as an explicitly labelled legacy override. Do not guess whether an explicitly serialized 30 was a player's choice or the old default. Opening settings does not clamp or silently rewrite it. Reset-to-default opts into 120; normal new selection uses 120–600. Subsequent new claims use the displayed effective value and freeze it. |
| Existing settings file but `smotherDays` missing | Import the old 30-day fallback for existing start-only claims; use new 120-day default for new claims after import. |
| Old claim with start tick only | On first import, compute its old effective due time using the imported legacy duration (30-day fallback if absent), then freeze it and record migration. This preserves what the prior build would currently owe, not an unknowable original duration if old settings had been changed historically. |
| New-schema claim with duration/due fields | Use saved values, never the current global setting. Detect corrupted/overflowed fields and report/recover deterministically rather than duplicate payout. |
| Feature disabled before/after due | Refuse new jobs; elapsed clock continues, due claim remains held. Re-enable processes once at the next normal claim pass. This is holding, not a paused timer. |
| Interrupted job before consumption or duplicate order | No claim/no consumed blanket for unsuccessful completion; existing claim not restarted or charged twice. |

Migration is idempotent across repeated load/save. Tests include absent/present/default/custom settings, due and not-due claims, simultaneous old/new claims, settings changes before and after import, disabled loading, repeated order and integer boundary/overflow. UI explicitly distinguishes imported accelerated overrides from the years-long normal default; the compatibility behavior is not described as new canonical timing. The one-way reset action is explicit and does not extend old due dates.

Do not wait two years or warp the populated colony clock. Check real production duration/boundary arithmetic offline at 119.999/120 days and at imported values; a disclosed proof-only scale compresses time intervals for the observed real scheduling/maturation path. The scaled timer and unscaled frozen duration must both be reported, and exact prior values restored. This establishes integration plus arithmetic, not real years of colony play.

## Premium cane usefulness

The current fuel patch adds cane to filters naming WoodLog; no separate premium duration/heat mechanism is present there. Source: `Patches/RM_DeadVenomvine_Fuel.xml:12`, item promise `RM_SmotherCraft.xml:75`. Acceptance must compare useful outcomes, not loaded filters or market value.

Agent initial tuning: one cane supplies **2 wood-equivalent fuel units** and a heat-coupled consumer emits **1.25 times its matched wood heat rate while burning cane credit**. The generator need not double instantaneous electricity and a stove need not double job speed; longer operating time/work/energy and hotter heating are separately demonstrated. This makes both long burn and hot burn meaningful. Same-count controls use three matched consumer types: campfire heating, fueled cooking/work and wood generator energy. Count by stackCount, not Thing count. Hold room geometry, quality, ambient, power demand and available work equal; observe fuel input, depletion and actual heat/work/energy. Compare heat rate over an equal active interval as well as integrated heat over equal item counts.

Prefer a small shared material fuel-value/heat adapter over a special cane-only stove or per-building patches. The first reaches existing supported wood-filter consumers; the special stove would fail wherever-wood-burns usefulness, and scattered patches duplicate accounting. Consult existing shared fuel work before implementing. Limit changes to consumers accepting the named fuel; ordinary wood and unrelated fuels keep their behavior.

Mixed fuel requires provenance: save ordered residual fuel-credit segments by material so consumption, heat bonus, refuel and reload cannot duplicate energy or apply cane heat after its credit is exhausted. Legacy anonymous fuel imports as ordinary fuel credit. Capacity clipping is explicit lost credit, never a hidden extra item or infinite carry reservoir: test full/almost-full containers, target fuel levels, mixed intake, off/on, despawn and reload. Positive premium comparison uses enough empty capacity for the whole measured input, so clipping cannot hide the ratio. Feature switches/tuning must be represented in the complete settings census when implemented. No new art is commissioned by this plan.
