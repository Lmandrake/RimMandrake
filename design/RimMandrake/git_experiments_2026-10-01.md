## E2 Concurrent writers via local bare remote
Setup: `/home/mandrake/wt/gitlab/e2_{a,b,c}/remote.git` (bare, cloned from the ext4 seat), 4 `--shared` sparse clones (cone `e2`), 4 python threads x 10 rounds. Each round: append own file, append 1 line to shared `e2/shared.md` + 1 jsonl line to `e2/shard.jsonl` (variant c: two NEW files under `e2/records/` instead), commit, then loop `git pull --rebase origin main && git push origin HEAD:main` (<=30 tries). Policy on a rebase conflict: `rebase --abort`, drop my commit, re-pull, redo the edit (counts as a retry). Script `/home/mandrake/wt/gitlab/e2.py`, output `e2.out`. Two full runs per variant, ~4.7 s each (40 commits).
- (a) no gitattributes: run1 conflicts 24 (rebase failed 24 times), ~38 retries, 12 push rejections; run2 conflicts 24, ~35 retries, 11 push rejections. 0 failed rounds, 0 lost lines (40/40 lessons, 40/40 jsonl, 40/40 own) ONLY because of the abort-and-redo policy; the default `pull --rebase` simply stops on every one of those conflicts (end-of-file appends to the same file conflict deterministically).
- (b) `merge=union` on `e2/*.jsonl` and `e2/*.md`: 0 conflicts both runs; all remaining retries (54 and 54) were plain push races (non-ff rejection then pull --rebase succeeded). 40/40, 40/40, 40/40, no duplicate lines.
- (c) one file per record: 0 conflicts, same push-race retries (54 / 54), 40/40 everywhere, nothing to merge at all.
Caveat: the sparse clones keep the index/disk tiny so rounds are fast and agents tend to run in lockstep (retry counts come in multiples of 9); the contention is probably higher than real but conflict behaviour is deterministic. union merge also relies on the attribute being committed before use and applies only to textual line-oriented files (it can reorder/duplicate lines if both sides touch the same existing line; not exercised).
## E3 git merge-tree --write-tree
git 2.53.0. Script `/home/mandrake/wt/gitlab/e3.py`, output `e3.out` (sparse clone of a local bare remote `e3/remote.git`; worktree never touched).
- both branches append a different line to end of same file: rc=1, prints tree OID + conflicted-file stage list (1/2/3 blobs) + "CONFLICT (content)"; the written tree holds the file WITH conflict markers (usable but not publishable).
- same-line edits: rc=1, same shape.
- rename on one side + edit of old path on the other (and rename vs append): rc=0, clean tree OID only (rename detection carried the edit across).
- pipeline `tree=$(git merge-tree --write-tree A B | head -1); c=$(git commit-tree $tree -p A -p B -m msg); git push <remote> $c:refs/heads/x` works: bare remote log shows the 2-parent merge, both `e3/log.txt` and `e3/new_name.txt` present, `git status --porcelain` and HEAD unchanged before/after (identical output). Also pushed `$c:refs/heads/main` onto a moved remote main with `--force-with-lease=main:<sha>` successfully.
- Conclusion: merge-tree gives a no-worktree, no-index, side-effect-free merge with exit code 0 clean / 1 conflict, so a publish tool can decide "clean -> push, conflict -> report" without ever touching the shared checkout. It does NOT resolve true same-region conflicts.
## E4 jj
Installed jj 0.45.1 (musl x86_64 release tarball) at `/home/mandrake/.local/bin/jj`. Test repo `/home/mandrake/wt/gitlab/e4/repo` (ext4 checkout of 29,494 files from local bare `e4/remote.git`).
- `jj git init --colocate` on the 29.5k-file tree: 1.27 s wall (includes first snapshot). Subsequent `jj st` x4: 0.02 s each (git status --porcelain on the same tree: 0.19 s here, a clean tree).
- Untracked files: jj AUTO-TRACKS every new file at the next command (50 junk files -> `jj file list` shows 50/50, status shows them as added); in the colocated repo git then sees them as ` A` intent-to-add, not `??`. Files over 1 MiB (5 MB junk) are NOT snapshotted: warning "Refused to snapshot some files ... snapshot.max-new-file-size" printed on every jj command until ignored/raised. Removing the files un-tracks them again ("working copy has no changes").
- `jj workspace add ../wsN` full checkout: 9.38 s, 12.56 s, 12.27 s (4.1G each); `--sparse-patterns empty`: 0.05 s.
- Concurrent simulation (4 workspaces: default + ws1..3, threads, 5 rounds each, shared appended `e4/shared.md`; loop = `jj git fetch; jj rebase -s @- -d main@origin; (conflict check); jj bookmark set main -r @-; jj git push -b main`). Scripts `/home/mandrake/wt/gitlab/e4c.py`, `e4d.sh`, `e4u.sh`; logs `e4/log_*.json`, `e4d.out`, `e4u.out`. Several naive-agent runs, outcomes (these are the NAIVE script's results, not best-case jj):
  - Op-log: "Concurrent modification detected, resolving automatically" fired 72-83 times per 4-agent/5-round run (op heads merged automatically, never blocked a command). Stale working copy ("The working copy is stale ... run `jj workspace update-stale`") hit 3-4 times per run: another workspace's op rewrote this workspace's @; recoverable with `jj workspace update-stale`, which prints a "(divergent)" working-copy commit once. Divergent changes (same change-id, 2 commits) appeared 5-30 times per run.
  - Conflict representation: with the shared append file jj never refuses the rebase; the conflicted commit is stored with a `(conflict)` flag and propagates to descendants (the status line printed "(conflict) (empty)" for wc). `jj git push` refuses it: "Won't push commit ... since it has conflicts". No markers land on main (0 conflict-marker lines on remote in all runs). jj does NOT honour `.gitattributes merge=union` (not exercised in a run; documented behaviour, UNMEASURED here).
  - Real hazards found: (1) the local `main` bookmark is repo-wide, shared by all workspaces; concurrent `bookmark set` produced "Bookmark main is conflicted" push errors; (2) `jj abandon @-` on a commit carrying `main` deleted the bookmark and the next push tried to delete remote main ("[delete from ...]", refused by git "deleting the current branch is denied"); (3) my redo policy used `--allow-backwards`, and the remote lost updates (13/20 and 11/20 of the intended lines on remote main with 0 reported failures).
  - D1 deterministic lost-update test (e4d.out): ws1 and ws2 both build on X; ws1 pushes c1 (move forward OK). ws2 `jj bookmark set main -r @-` -> "Refusing to move bookmark backwards or sideways" (good guard). With `--allow-backwards`, `jj git push -b main` printed "move sideways from 051c619b145d to 23a99c12892e" and SUCCEEDED: remote main became c2 and c1 was dropped from main (c1 file count 0, c2 file count 1). So jj's push lease is against jj's shared remote-tracking view, not the commit the agent built on: non-fast-forward is refused only by the bookmark-set guard, never by push.
  - `jj undo` (e4u.out): ws1 and ws3 each committed (A_work, B_work); ws1 ran plain `jj undo` and it undid the globally most recent operation, i.e. ws3's `commit` (B_work). Afterwards A_work still existed, B_work no longer existed, and ws3's `jj st` showed its file as an uncommitted add on a description-less wc commit. Op log is shared across all workspaces, so plain `undo` is not scoped to the caller; `jj undo <op-id>` or `jj op restore` would be needed to target one's own.
- Push refuses non-ff? Only via the `bookmark set` guard (above); `jj git push` to bare remote itself works (seed push OK, c1 push 'move forward' OK).
