# RimWorld new version research (2026-10-20)

Method: web search plus fetches on 2026-10-19/20 (secondary sources are search-engine summaries unless marked FETCHED). Nothing here was tested on our install.

## 8 facts that matter for Wave 3 deploy and our C#/Harmony DLLs

1. **Owner is right about the news, but it is NOT on the default branch.** Ludeon announced Update 1.7 and the new in-house **Waylith Engine** (replaces Unity) on 2026-10-12; it is only on Steam's opt-in **`unstable`** beta branch. Main branch stays 1.6. FETCHED: https://ludeon.com/blog/2026/10/announcing-the-waylith-engine-and-update-1-7/ (2026-10-12); FETCHED: https://steamcommunity.com/app/294100/allnews/ (newest item is that post; no 1.6 update after 1.6.4850 of Jun 8 listed).
2. **Our install cannot have auto-updated into it.** Local appmanifest has no BetaKey line (grep of betas returned nothing), buildid 23969874, Version.txt 1.6.4871 rev590. A game only moves to 1.7 if someone selects `unstable` in Steam Betas. (Local file: `/mnt/c/Program Files (x86)/Steam/steamapps/appmanifest_294100.acf`, checked 2026-10-19 21:40 PDT.) Note `AutoUpdateBehavior` is 0 (always update), so a later main-branch 1.7 release WOULD land automatically; see section 4.
3. **Performance claim, Ludeon's own tests:** 2-4x; late-game colony 2.2x; a 1500-mod pack loads in 6 min vs 14 (FETCHED, Ludeon blog above). Owner's "just goes faster" is accurate; frame-rate gains are unverified (Xenospectrum, search summary: https://xenospectrum.com/en/rimworld-waylith-engine-unity-migration/). Beta configs reportedly use about 12-13 GB RAM at startup (FETCHED: https://finalboss.io/rimworld-1-7-beta-performance-mod-compatibility-and-ram-usage, 2026-10-14).
4. **Our C# DLLs: 1.6-built assemblies are expected to load via a shim (Unity calls translated to Waylith), roughly "99%" out of the box, no rebuild needed** (FETCHED: https://rimworldwiki.com/wiki/Modding_Tutorials/RimWorld_1.7_Mod_Updates, page edited 2026-10-18; the 99% figure came from the search summary of that page, the fetched text says only "most 1.6 mods should work without rebuilding"). Ludeon: "most mods work without changes"; mods may show a yellow "potentially unsupported" only because the version number changed (Ludeon blog).
5. **To build FOR 1.7 (not needed to run on 1.7):** target `net10.0` (needs VS2026/recent Rider), remove Unity DLL refs, reference Assembly-CSharp.dll, UnityStubs.dll, Waylith.dll; libraries/frameworks "must be rebuilt for the new engine" (wiki, FETCHED). 1.6 stays on the Harmony 2.4.x line (HarmonyRimWorld v3.0.0.0 notes: 1.6 library updated to 2.4.3).
6. **Harmony is the main risk for our patches.** 1.7 uses Harmony 3 on .NET 10; it type-checks `__instance`/`__result` injections and rejects mismatched patches; v3.0.1.0 (15 Oct) "Invalid patch IL is rejected during installation" (FETCHED: https://github.com/pardeike/HarmonyRimWorld/releases, day/month only, year not shown). **Prepatcher-dependent mods stop working until Prepatcher updates; I found no 1.7 Prepatcher release.** Real failures reported on build 1.7.4979 (unstable): a mod patch error with Harmony 3.0.0-rc.3 (search summary; https://github.com/Ionfrigate12345/Rimworld_SOS2VEEPatch/issues/1 and https://steamcommunity.com/sharedfiles/filedetails/?id=3652938473).
7. **Art / shaders:** 1.6 AssetBundle shaders should still load; new shaders must be GLSL; 1.7 uses Vulkan and loads the **Linux** build of bundle shaders, so Windows-only bundles will not load; 1.6 bundles "no longer necessary" and assets are cached on first load (wiki, FETCHED). Case report of five separate shader problems incl. baked blend state: https://github.com/Jeffrharr/CelestialLighting/issues/257 (search summary). Saves: 1.6 saves load in 1.7 and 1.7 saves go back to 1.6 (Ludeon blog).
8. **Tooling changes that will break OUR scripts if we ever test on 1.7:** Player.log moves to a `Logs` folder under `AppData\LocalLow\Ludeon Studios\RimWorld by Ludeon Studios\`; Doorstop no longer needed; new `-mod=` launch arg; Frame Profiler in dev mode (wiki, FETCHED). Our bridge/JawaBench/Player.log-reading instruments assume the 1.6 layout.

**Bottom line for Wave 3:** stay on main (1.6.4871). No default-branch update exists as of 2026-10-19. A 1.7 test is only worth doing on a separate copy/branch after our DLLs are checked for Harmony 3 type rules; the `unstable` build is a moving beta (1.7.4979 rev109 reported).

## 4. Pin / roll back (app 294100)
Evidence status: the Steam steps below are standard Steam client behaviour from general knowledge plus one search result; no RimWorld-specific official rollback page was found.
1. We are already on main, so there is nothing to roll back; do not touch the Betas tab. If anyone selects `unstable`, undo by Steam > RimWorld > Properties > Betas > dropdown "None - Opt out of all beta programs"; saves are two-way compatible per Ludeon, but mod configs and Player.log location differ.
2. Delay updates: Properties > Updates > Automatic updates > "Only update this game when I launch it" (confirmed in a search result, https://www.laptopmag.com/articles/prevent-steam-auto-update-games). Our manifest currently has `AutoUpdateBehavior` 0. This is a delay, not a hard block: Steam still updates when the game is launched from Steam.
3. Hard pin (general practice, not verified here): close Steam, copy `C:\Program Files (x86)\Steam\steamapps\common\RimWorld` and `appmanifest_294100.acf` to a backup (this is the only reliable local rollback, as one Nexus user did for another game: https://forums.nexusmods.com/topic/13184316-bg3-in-steam-permanently-disabling-automatic-updates); optionally mark the .acf read-only after setting `AutoUpdateBehavior` to 1 while Steam is closed. Launching via the game exe directly (not Steam) avoids the launch-time update.
4. Test-only 1.7 install without touching the main copy: not verified; the safe route is a second Steam library or a full folder copy opted into `unstable`, never the live `Mods` folder we deploy to.
5. I found no Steam "previous version" beta branch for RimWorld; none is mentioned by Ludeon. The only branch named is `unstable`.
