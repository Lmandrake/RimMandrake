## 1. The reviewer that rewrites itself

**Worth adapting, with the boundary above.** The daily workflow collects a corpus and invokes a synthesizing agent (`W:templates/github/workflows/improve-review-pr.yml:12–21,41–100`). The skill rejects one-off or already-encoded lessons, permits a no-op, separates portable guidance from repo-local guidance, and opens a PR that it explicitly must not merge (`W:.agents/skills/improve-review-pr/SKILL.md:61–129`). Thus “rewrites itself” means **proposes a reviewed instruction edit**, not an autonomous self-modifying acceptance policy.

The collector is real code, but the advertised human signal is weaker than it sounds (`W:.agents/skills/improve-review-pr/scripts/collect_review_feedback.py`):

- `:118–124,228–255` accepts any bot login or matching review-body markers as agent attribution; it does not establish the exact trusted review producer.
- `:140–187` labels replies by substring: “thanks” can count as validated, and a long unrecognized reply becomes refined. This conflicts with the skill's instruction to ignore mere acknowledgements (`SKILL.md:59`).
- `:303–342` keeps issue comments using keyword matching, without linking them to one finding. `:345–366` dates reaction eligibility by the original comment's creation time; a new reaction to an older comment can be missed. Reaction totals supply no reactor identity or individual reaction timestamp.
- `:190–209` caps the recently updated PR search (default 50); `:220–222` reads reviews/comments, not a product diff establishing that a suggested fix was actually made. “Accepted/fixed/ignored” is not independently measured by this collector.

**UNVERIFIED:** run success, useful feedback volume, adoption rate, false-learning rate, and any actual improvement. A daily no-op is explicitly valid; the source alone cannot tell whether that is its usual result.

We already curate machine findings and sample closed-item proofs (`R:src/RimMandrake/Utils/findings_judge_prompt.md:7–32`), and Friday writes general patterns into skills/facts (`findings_judge_friday.md:2–7`). The shell actually loads those packets by day (`findings_judge.sh:15–23`), on a daily timer (`systemd/rm-findings-judge.timer:4–6`). Those entry points do **not** explicitly collect owner corrections to individual review outputs. That is the scoped gap, not an absence of all self-improvement here. The art code above already provides the better local model.

## 2. Per-story parallel verification

**No adoption of concurrent live-game scenes; speedup is unmeasured.** The actual skill says bounded fan-out of about 4–6 **independent stories**, with serial handling for reproduction, sequential stories or scarce credentials. It does not promise one worker for every acceptance criterion (`W:.agents/skills/verify-behavior/SKILL.md:41–64`). Its contract now delegates through dedicated `computer_use`; the setup skill's older Chrome/Puppeteer description should not substitute for that narrower contract (`verify-behavior/SKILL.md:17–33,80`; `oz-cloud-factory-demo/SKILL.md:36`).

Our round enumerates `(item, criterion, proof, sha)` and runs them sequentially (`R:src/RimMandrake/rimflow/relentless_live_round.py:821–885`); an exclusive round lock also prevents overlapping rounds (`:1049–1053`). The game lane enforces one live user, and the proof runner takes/releases the bridge around the proof (`relentless_game.py:7–34`; `relentless_live.py:2212–2221,2283–2289`). This is a mutable shared game, not independent cloud app sandboxes. More agents would mostly queue for that resource or interfere with staging and restoration. State-reading proofs are not automatically safe to interleave with another scene's writes.

Parallel judgment of **already captured** scenes is technically possible, as is independent verification on genuinely separate game instances. Neither has a measured payoff in this study; no fan-out implementation or benchmarking item is justified just by Warp's prose. Our existing modcheck already judges specific visual statements after deterministic capture (`R:src/RimMandrake/Utils/modcheck/judge.py:11–20,68–80`). Keep interaction scenes and the complete walk: `designer_stage.py:569–592` explicitly prevents an interaction from replacing each feature's own acceptance scene.

## 3. Two checked-in specs and a validator

**Our intake floor is more explicit; their external validator remains unassessed.** Warp's coordinator writes `specs/<issue-slug>/PRODUCT.md` and `TECH.md`, separating behavior/non-goals/acceptance from approach/alternatives/validation (`W:.agents/skills/spec/SKILL.md:91–129`). It waits for review before readiness unless the consuming repo opts out (`:160–162`). Implementation must compare against specs, but allows manual comparison if the helper is missing, and can proceed without specs (`implementation/SKILL.md:20–24,86–105,142–149`).

The three common skills, including `validate-changes-match-specs`, are **not checked into this source revision**: the installer and workflows download them from `warpdotdev/common-skills` without an explicit commit pin (`W:scripts/install-cloud-factory.sh:22–23`; `templates/github/workflows/implement-ready-issues.yml:30–31`). They were not installed or executed here. There is no basis to claim that external validator is stronger or weaker internally than ours. The local review skill does explicitly compare commitments to the diff, which is useful behavior but already part of our clause-oriented judging (`W:.agents/skills/review-pr/SKILL.md:89–91`; `R:src/RimMandrake/rimflow/relentless_wall.py:47–63`).

Our code mechanically rejects unmapped promises and open core questions (`R:src/RimMandrake/rimflow/concept_tree.py:185–255`); requires meaningful red cases, named false-pass worlds and an oracle/cannot-show declaration (`:256–324`); checks floor hashes and north-star coverage (`:327–427`); and requires current signed coverage, validated root and sourced owner waivers (`:656–700`). `relentless_refusal():718–742` applies that gate to mods and every cited tree. ## 4. Event triggers versus timers

**Keep our hybrid; no migration.** Warp handles opened issues, readiness labels and non-draft PR events (`W:templates/github/workflows/triage-issues.yml:17–24`; `spec-ready-issues.yml:8–23`; `implement-ready-issues.yml:7–22`; `review-pull-requests.yml:16–28,55–62`). That makes routing visible and prompt, with per-issue/PR concurrency controls. It also has a daily timer for improvement. The repo itself warns that labels written with `GITHUB_TOKEN` may not trigger the next workflow (`W:.agents/skills/oz-cloud-factory-demo/SKILL.md:329–345`); a chain of YAML events is not proof of a working end-to-end factory.

Our event wake already coalesces publish/job-completion notifications and retains a timer heartbeat for missed/capped notifications (`R:src/RimMandrake/rimflow/relentless_wake.py:7–24`, implemented by `poke`, `fire`, `serve`; `Utils/systemd/rm-relentless-wake.path:12–14`). `priority.py:60–94` filters work by satisfiable needs, including bridge/owner constraints. Reconciliation is useful when the next action depends on deployment, game identity and resources, rather than just a label. Timers cost periodic reads; events cost delivery, duplication and ordering handling. We already have both mechanisms. This is a code comparison, not a claim that those units' current live status was measured.

## What we do better, and attractive parts we already have

**Acceptance and reviewer independence.** Warp supplies an instruction-driven implementation/spec comparison and a JSON/location validator. Ours separates blind marking at an exact commit from building (`R:src/RimMandrake/rimflow/relentless.py:4889–4911`), fences reports by lease/nonce (`:1523–1566,1963–1999`), and distinguishes product failure, weak proof and unreachable evidence. `relentless_wall.py:74–110` writes and checks structured `verdict.json`, including controls for product defects. Warp's binary `APPROVE/REJECT` with severity-prefixed comments (`W:.agents/skills/review-pr/SKILL.md:68–75,93–110`) would lose useful distinctions here. Nothing to take by renaming our artifact `review.json`.

**Evidence handling.** Their review workflow is a good concrete design: trusted checkout, untrusted diff, read-only review job, separately privileged publisher, annotated coordinates and stale base/head refusal (`W:templates/github/workflows/review-pull-requests.yml:69–98,195–216,321–377`). The validator checks locations, severity prefixes and duplicated suggestion context; it cannot establish semantic correctness (`W:.agents/skills/review-pr/scripts/validate_review_json.py:138–175,178–320,333–378`). Our receipts additionally chain and seal evidence by item/SHA (`R:src/RimMandrake/rimflow/evidence.py:7–31,425–469`). Existing showing stations already carry `shows`, `judge`, `capture`, deployment fingerprints and independent prereview (`relentless_showing.py:237–265,321–365,520–539`). Captions and evidence-linked checklists are good advice already embodied here; a second manifest would duplicate them. Neither design makes an inaccessible artifact proof.

**Skill shape and triage.** Their small stage skills with constrained local companions are reusable (`W:.agents/skills/review-pr/SKILL.md:22`; `improve-review-pr/SKILL.md:84–104`). Our staged Designer packets already separate role concerns (`R:src/RimMandrake/rimflow/roles/designer.md:35–44`), and worker names are replaceable configuration (`relentless.py:4–6`; `relentless_rules.json`, `worker_agent`/`checker_agent`). Their four readiness labels clearly distinguish missing information from worthwhile complex work and premature work (`W:.agents/skills/triage/SKILL.md:75–124`), but need not become another state axis alongside our needs, blockers and Designer gate. The apply job checks nonempty state/label, not an allowlisted four-state schema (`triage-issues.yml:403–431`), so even exclusivity is partly an instruction rather than a hard guarantee. **No new labels or skill-install system.**

**Portable worker contract.** `M:relentless/workers/BUILDER_JUDGE.md:89–127` specifies a blind packet, fresh marking, exact-SHA reruns and cause-class routing; `:26–40` specifies an independently set and validated exam in shadow. The latter is a worker contract, not proof that every clause is already enforced in RimMandrake. Its explicit acknowledgment of correlated model blind spots (`:129–134`) is more candid than inferring independence from Warp's separate review stage. Retain that discipline, the builder/test-builder/judge shape and the retired status of FOUNDRY.
