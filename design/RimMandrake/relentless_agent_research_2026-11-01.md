# The Relentless Agent: research brief (2026-11-01)

Input to `design/RimMandrake/relentless_agent_design_2026-11-01.md`. Target: Build and Judge modes, memory between generations, loop-trap awareness, calling for review and help, reusable with RimMandrake first.

**Method limit.** No web-search tool in this seat: pages were fetched by curl from known URLs and arXiv title searches, so coverage has selection bias. Every cited URL was fetched and read unless listed under "Sources not verified". 2026 arXiv ids are preprints, not peer reviewed.

## Evidence key

- **[C]** controlled or benchmarked study, numbers published.
- **[V]** vendor report with its own numbers, not independently repeated.
- **[P]** practitioner account or code; anecdote, or thresholds chosen by engineers.
- **[D]** design doctrine; argument, no measurement.
- **[L]** measured by us: relentless store, read-only, first ~1.5 days, 2026-11-01.

**Where we stand [L].** 75 items, 48 done, 34 of the 48 with 0 returns. 66 blind checks, 16 fails (~24%). 57.8M weighted tokens spent; median done item ~0.76M, max ~4.5M. 559 `check_waits` tick rows (ticks, not items, mostly the clone pool at cap 10). `learned.md` ~104 KB in total, biggest ~9.5 KB. **The judge's false-pass rate is unmeasured, and so is whether its 16 fails were right.** Nothing is known yet about how good "done" is.

## 1. Ralph loop practice

- **The practice is well described and almost untested.** I found no controlled trial of Ralph on software. The one controlled result is off-domain: "Supervising Ralph Wiggum" (battery pack design) found a metacognitive co-regulation agent beat self-regulation and a plain loop without significantly more cost [C, one domain] https://arxiv.org/abs/2603.24768. Our 2026-10-29 sim backtest failed (`ralph_loop_design_2026-10-29.md`). **For us:** the loop is justified by design argument and our own journal, so instrument it as an experiment.
- **One item per loop, state on disk, fresh context.** Huntley: one item per loop, quality falling as the window fills, "deterministically bad in an undeterministic world" [P] https://ghuntley.com/ralph/. snarktank: memory is only git, append-only progress, and `prd.json` pass flags; items sized for one context [P] https://github.com/snarktank/ralph. **For us:** we already do this. Item size is a design input: an item that cannot fit one context cannot be looped into shape.
- **Fix the failure domain, not the instance.** "When you see a failure domain, resolve it so it never happens again" [P] https://ghuntley.com/loop/. But signs accrete: "Eventually all Ralph thinks about is the signs" [P] https://ghuntley.com/ralph/. **For us:** recurring classes leave the loop and become gates in code, not more prose for workers.
- **The plan is disposable.** Regenerating a plan costs one loop; a wrong plan costs circles. Planning and Building are separate modes [P] https://github.com/ClaytonFarr/ralph-playbook. **For us:** Build mode needs a sibling Plan or Redesign step, and it is what our pilot/redesign state already is.
- **The verifier sets the ceiling.** Anthropic's C compiler: Ralph-style, 16 agents, ~2,000 sessions, ~$20k, 100k lines. The task verifier must be "nearly perfect, otherwise Claude will solve the wrong problem". All agents hit one bug on the single giant kernel task until a GCC oracle allowed bisecting. Failed approaches were kept in a running doc; test output was trimmed to a few lines; the default test run was a deterministic per-agent 1%/10% sample [V, one run] https://www.anthropic.com/engineering/building-c-compiler. **For us:** spend on the verifier first. Sampling per worker is a cheap test-economy idea to try (section 5).
- **Coordination by shared lock file failed at scale.** Cursor: 20 agents gave roughly the throughput of 2-3 until replaced by planners, workers and a judge; "Many of our improvements came from removing complexity" [V] https://cursor.com/blog/scaling-agents. **For us:** central supervisor and per-item clones are the right side of this. Keep the supervisor free of AI.

## 2. Anthropic guidance

- **Named failure patterns match ours.** One-shotting, a later instance seeing progress and declaring done, marking complete without proper testing. Fix: a JSON feature list where only `passes` changes, a progress file, a start-of-session smoke test, a clean end state. Vendor calls long-running agents an "open problem" [V, qualitative] https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents. **For us:** add the start-of-session smoke test if the worker prompt lacks one. It is cheap and catches a dirty inherited clone.
- **A separate evaluator is easier to tune than a self-critical builder, but it is lenient by default.** Quote: "tuning a standalone evaluator to be skeptical turns out to be far more tractable than making a generator critical of its own work"; yet "the evaluator is still an LLM that is inclined to be generous towards LLM-generated outputs". Out of the box it talked itself out of real issues and tested superficially; it was tuned by reading logs where its judgment diverged, with few-shot calibration [V, n~1; full harness 6 h $200 vs solo 20 min $9] https://www.anthropic.com/engineering/harness-design-long-running-apps. **For us:** `rm-judge` needs a tuning loop of its own, driven by logged disagreements.
- **Contract negotiated before code.** Same source: generator and evaluator agreed a sprint contract before building; criteria wording steered the generator. **For us:** our contract is written by the first worker alone (section 6).
- **Every harness part is an expiring assumption.** "Every component in a harness encodes an assumption about what the model can't do on its own"; sprints were removed on Opus 4.6, and "the evaluator is not a fixed yes-or-no decision". Context resets became "dead weight" on Opus 4.5 per https://www.anthropic.com/engineering/managed-agents [V, opinion from experience]. **For us:** tag each rule with the assumption it encodes and an ablation test, so a new model can retire it. Note the tension: we chose fresh context for fencing and crash recovery, which holds regardless of model.
- **Interfaces meant to outlast implementations.** Managed Agents splits session (append-only log), harness and sandbox; "pets vs cattle"; `execute(name,input)`, `wake(sessionId)`, `getEvents()`; session is not the context window; compaction is irreversible; credentials stay outside the sandbox [V, architecture] https://www.anthropic.com/engineering/managed-agents. **For us:** close to our item, journal and clone. Use it as the check on port names (section 7).
- **Start simple.** Add complexity only when needed; frameworks obscure; evaluator-optimizer fits when criteria are clear and refinement has measurable value [D] https://www.anthropic.com/engineering/building-effective-agents.
- **Context.** Smallest high-signal set, right altitude, just-in-time identifiers [D] https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents. The memory tool is client-side, warns "ASSUME INTERRUPTION", and needs path traversal protection [V docs] https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool. **For us:** a generation gets pointers plus a few lines, not a narrative.
- **Packaging limit.** Plugin subagents ignore `hooks`, `mcpServers` and `permissionMode` https://code.claude.com/docs/en/sub-agents; plugins bundle skills, agents, hooks and MCP https://code.claude.com/docs/en/plugins. **For us:** a plugin cannot carry fencing. The supervisor stays a program outside the agent; plugin or skill is at most the worker-facing skin. Skills format: https://agentskills.io/specification. Agent loop: https://www.anthropic.com/engineering/building-agents-with-the-claude-agent-sdk.

## 3. Memory across fresh contexts

- **Context files often hurt.** Evaluating AGENTS.md (SWE-bench and CTXbench): context files did not generally raise success and raised cost ~20%; repository overviews did not help; developer-written beat LLM-generated by ~7%; authors advise omitting LLM-generated files [C] https://arxiv.org/abs/2602.11988. **For us:** this is the strongest single warning against rich `learned.md`. No overviews, no narrative; only what the repo does not already say.
- **Keep it small and tied to a task signal.** Reflexion bounded memory to 1-3 reflections and reached 91% vs 80% on HumanEval, using verbal reflection on feedback from tests [C, benchmarks] https://arxiv.org/abs/2303.11366. **For us:** a tight cap on what is injected into a worker. Reflections come from the failure evidence, not the worker's story of its session.
- **Verify at read, not at curation.** GitHub Copilot stores memories with citations and checks them just in time: "hard to solve, but easy to verify". Seeded adversarial memories were detected and self-healed. Reported +7% PR merge rate (90 vs 83), review precision +3%, recall +4% [V, measured] https://github.blog/ai-and-ml/github-copilot/building-an-agentic-memory-system-for-github-copilot/. **For us:** the best available pattern. Each `learned.md` entry carries file, sha or commit, and claim; a worker re-checks before relying on it; a failed check deletes the entry. Our threat is stale, not hostile, and this handles both.
- **Sleep-time consolidation pays only if future needs are predictable.** ~5x less test-time compute and up to 13%/18% accuracy on math benchmarks [C, far domain] https://arxiv.org/abs/2504.13171. Letta's plain-file agent scored 74% on LoCoMo, and Letta doubts such benchmarks mean much [V] https://www.letta.com/blog/benchmarking-ai-agent-memory. **For us:** plain files are enough. A consolidation pass could be a tick-time job later; there's no evidence it earns its keep at ~104 KB across 75 items.
- **Poisoned memory is real, stale memory is ours.** AgentPoison got >80% attack success with minimal poison [C] https://arxiv.org/abs/2407.12784; MINJA injected through queries alone https://arxiv.org/abs/2503.03704. **For us:** workers are honest, but a confused worker writes the same shape of defect. Never let a learned entry reach the judge (already ruled in our design).
- **Accumulating rules: weak evidence.** 11 sessions, self-report, rules 5 to 18 [weak] https://arxiv.org/abs/2607.13091. Do not cite it as support.

## 4. Detecting loops and thrashing

- **No measured threshold exists that I could find.** OpenHands uses 4 identical action+observation pairs, 3+ monologue steps, a 6-step alternation, 10+ context-error events; these are engineering choices [P] https://raw.githubusercontent.com/All-Hands-AI/OpenHands/0.59.0/openhands/controller/stuck.py. Aider allows 3 reflections [P] https://github.com/Aider-AI/aider/blob/master/aider/coders/base_coder.py. **For us:** our 3 and 9 are as defensible as anyone's; tune them against our own journal, and say so.
- **Self-diagnosis is unreliable.** Who&When: best automated attribution 53.5% for agent, 14.2% for step, some below random [C] https://arxiv.org/abs/2505.00212. **For us:** `same_failure_limit` counts worker-given slugs, which rest on this weak ability; the design already had to handle rotating slugs. Fingerprint what the supervisor can read itself: normalised failing test ids and error lines, diff hash against the previous return, gate name.
- **Repetition is a minority of failure, and exact matching misses meaning.** MAST (1,600+ traces, kappa .88): step repetition 15.7%, no or incomplete verification 8.2%, incorrect verification 9.1%, premature termination 6.2% [C] https://arxiv.org/abs/2503.13657. **For us:** a loop detector alone will not catch most failure. Exact fingerprints are the floor; a semantic check (the same idea in new words) is unmeasured and should be a judged sample before it becomes a rule.
- **Cheap progress signal.** Failed trajectories run consistently longer with higher variance, and 72-81% found the right files even when failing [C] https://arxiv.org/abs/2511.00197. **For us:** spend and step outliers per item are a good trigger for review. Finding the right file is not progress.
- **Asking for help works on deadlock.** 150 manually studied failures: most agentic failures were flawed reasoning and cognitive deadlocks; an Expert-Executor supervisor solved 22.2% of previously intractable cases [C, small] https://arxiv.org/abs/2509.13941. With arXiv 2603.24768 this is the only evidence for "call for help". **For us:** the help trigger should fire on no-progress fingerprints, give the helper the evidence, and be counted by whether the next return moved.

## 5. Test economy

- **Sound caching depends on declared inputs, and leaks are the known failure.** Bazel: "does not track tools outside a workspace", env vars leak, and the docs give a procedure for a poisoned cache [D/P, production docs] https://bazel.build/remote/caching, https://bazel.build/basics/hermeticity. `external` forces a run, `flaky` retries up to 3 https://bazel.build/reference/be/common-definitions. **For us:** key on hash of tests, code, tool versions, env, data. Default is a miss; unknown input means a run.
- **testmon cannot see our main failure surface.** It tracks Python code, env vars and versions, but "doesn't know and doesn't track" static files such as XML and assets, nor external services [P docs] https://testmon.org/. **For us:** do not adopt selection by Python coverage for anything touching mod XML; a suite tracer that sees file reads (the `suite_trace` work now in the tree) fits better, and needs its own check.
- **Selection tools have bugs of their own.** RTSCheck found 27 bugs in Ekstazi, Clover and STARTS, covering safety and precision [C, ICSE'19] https://users.ece.utexas.edu/~gligoric/papers/ZhuETAL19RTSCheck.pdf. **For us:** the cache is a grader. Seed changes that must cause a miss, and run random audit reruns of hits, per `grader-validation`.
- **Predictive selection is deliberately unsafe.** Meta halved infra cost while catching >95% of test failures and >99.9% of faulty changes [V, production] https://arxiv.org/abs/1810.05286. **For us:** fine for a worker's fast loop. Never in the judge: the judge reruns proof cold, and the economy goes in the worker's inner loop.
- **Flakes corrupt signals.** Google: 1.5% of runs flaky; ~84% of observed pass-to-fail transitions involved a flaky test [V] https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html. **For us:** a flake looks like a repeated failure, and so can eat `same_failure_limit`. Quarantine or confirm before counting.

## 6. Independent evaluation

**Answer: a fresh context of the same model is a partial remedy. It removes anchoring on the worker's reasoning; it does not remove shared blind spots.**

- **Attribution helps.** Models fixed external errors but missed the same errors presented as their own: 64.5% blind spot across 14 open non-reasoning models [C, not frontier models] https://arxiv.org/abs/2507.02778. Supports fresh context and our ban on attempts and notes.
- **Errors correlate.** Across 350+ LLMs, models agree 60% of the time when both err; large accurate models correlate even across providers [C] https://arxiv.org/abs/2506.07962. Knight and Leveson 1986 found the same in independent human teams (IEEE TSE 12(1), read via https://en.wikipedia.org/wiki/N-version_programming). **For us:** a second vendor is partial independence, not a cure.
- **Review can regress.** 116 paired LiveCodeBench tasks: Claude reviewing Codex 71.6 to 89.7; Codex self-review 71.6 to 84.5; Codex reviewing Claude 91.4 to 82.8; Claude self-review 91.4 unchanged. Reviewers could not run code and had to output a final program; authors call it exploratory [C, competitive programming] https://arxiv.org/abs/2607.21656. **For us:** value depends on the gap, and a judge must judge, not rewrite. Do not read this as "use the other vendor".
- **Own-model favouritism is doubtful; preference for model text may not be.** AI-AI bias https://arxiv.org/abs/2407.12856 (PNAS 2025); reanalysis found no detectable own-model premium, +0.019, p=.14 https://arxiv.org/abs/2610.00369 [C, single author]. **For us:** do not spend on anti-favouritism; spend on leniency.
- **Tests passing is not correct.** PatchDiff: 7.8% counted correct while failing the developer suite; 29.6% of plausible patches behave differently; 28.6% of those certainly wrong [C] https://arxiv.org/abs/2503.15223. METR: 4 maintainers, 296 PRs, about half of test-passing PRs would not be merged, ~24 points below the grader; not a capability ceiling, since agents got no retry [C, small] https://metr.org/notes/2026-03-10-many-swe-bench-passing-prs-would-not-be-merged-into-main/. **For us:** "proof reran green" is necessary and far from sufficient. The judge's reading of the contract against the item carries real weight.
- **Worker-written proof is weak.** LLM-generated tests mainly capture actual rather than expected behaviour [C] https://arxiv.org/abs/2410.21136. **For us:** this is the leak in our design. The first worker writes the contract and the proof, then the judge opines on whether it's too easy. Candidates: a separate contract pass before any edit by an agent that will not build; hold-out checks in judge-only storage per `evaluation-independence`, enforced by filesystem; a third case, the contract coming from the item author.
- **Verifiers are superficial even when told otherwise.** MAST https://arxiv.org/abs/2503.13657 [C]; Anthropic above [V]. **For us:** the judge prompt alone is not the fix.
- **Seed defects, scoped to the diff.** Meta ACH: 10,795 classes, 9,095 mutants, 571 tests, 73% accepted; equivalent-mutant detector precision .79, recall .47 [V, production] https://arxiv.org/abs/2501.12862. Google: incremental mutation in code review, filtered, 24,000 developers [V, production] https://arxiv.org/abs/2102.11378. **For us:** run a small planted-fault stream through the real judge, indistinguishable from real candidates: a catch rate per defect class is our only route to the false-pass number. Control: hand-labelled known-good diffs, so a judge failing everything scores badly too. Keep planted items and any held-out labels unreachable from the judge's clone. Equivalent mutants mean some "misses" are not misses, so a human or second reader labels them.

## 7. Packaging for reuse

No measurement exists here; all of this is doctrine [D]. Weigh it accordingly.

- **Ports and adapters fit.** Goal is to "be developed and tested in isolation from its eventual run-time devices and databases" https://alistair.cockburn.us/hexagonal-architecture/. Proposed ports, drawn from live code rather than imagined: Store, Runner (fresh worker unit), Workspace (clone), Tracker (ledger), Proof (gates), Judge, Notifier, Spend meter, plus Rules as data. RimMandrake is adapter 1. Check [L]: `relentless.py` is 2,372 lines with 7 lazy project-import sites and 27 lines naming seats, rimflow or systemd, which suggests a small seam, not a rewrite. That count is a grep, a floor on the coupling.
- **Do not generalise early.** "Duplication is far cheaper than the wrong abstraction" https://sandimetz.com/blog/2016/1/20/the-wrong-abstraction; rule of three https://en.wikipedia.org/wiki/Rule_of_three_(computer_programming). Frameworks obscure (Anthropic above). **For us:** one real adapter plus one toy fixture repo that exists only to keep game words out of the core. No plugin system, no provider matrix, until a second real user.
- **Conformance beats documentation.** Kubernetes treats conformance as what makes implementations interoperable https://www.cncf.io/training/certification/software-conformance/. **For us:** the design's planted-fault table becomes a conformance suite, run against both adapters. It is both our reuse contract and a grader test.
- **Version every record.** Hyrum: "all observable behaviors of your system will be depended on by somebody" https://www.hyrumslaw.com/. SemVer https://semver.org/; MCP's dated versions and capability negotiation https://modelcontextprotocol.io/specification/2025-11-25. **For us:** `schema_version` on state, receipt, verdict, journal. Declare which fields are contract. Tolerate old records on read.
- **Durable execution is prior art for the store.** Temporal: event history and replay, with determinism constraints https://docs.temporal.io/workflow-execution. **For us:** reference for tests of crash recovery; adopting it would add a server for a problem our tick plus journal solves.
- **Modes as data.** Build and Judge should differ by a declared profile (what it may read, write, run; what it outputs), so the non-input wall is a checked field, not prompt prose. This is my inference from `evaluation-independence`, not a sourced result.

## What should change the design

1. **Measure the judge.** Seeded defects plus known-good controls, catch rate per class. The 24% fail rate says nothing about false passes (section 6).
2. **Stop the worker writing its own exam.** Contract by a non-builder, hold-outs in judge-only storage, enforced by filesystem (section 6).
3. **Memory: few, cited, verified at read.** Cap entries, cite file and sha, delete on failed check, no overviews or narrative (section 3).
4. **Loop signals from evidence, not slugs.** Supervisor-computed fingerprints and no-progress; thresholds tuned on our journal; help fires on deadlock and is scored by movement (section 4).
5. **Cache is a grader: default miss, hashed declared inputs including XML and tools, never in the judge, audited by seeded changes** (section 5).
6. **Reuse: ports around live code, conformance from the fault table, a toy second adapter, no framework. Tag every rule with the assumption it encodes** (sections 2, 7).

Also owed, smaller: judge wait is a real cost (559 tick rows); measure it per item before buying more clones.
