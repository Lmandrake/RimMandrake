# Git workflow research, 2026-10-01

## 1. Claude Code worktree control
Sources: https://code.claude.com/docs/en/hooks , https://code.claude.com/docs/en/worktrees , https://code.claude.com/docs/en/settings-reference (WebFetch summaries; fetched 2026-10-01).

- **YES, a `WorktreeCreate` hook replaces default creation entirely**, for `--worktree`, subagent `isolation: "worktree"`, and background sessions (hooks page). "Configure a WorktreeCreate hook to replace the default git worktree logic entirely, including placing worktrees somewhere other than `.claude/worktrees/`" (worktrees page, "Replace worktree creation with a hook").
- **Input** (stdin JSON, command hook): common fields (`session_id`, `transcript_path`, `cwd`, `hook_event_name`, ...) plus `name`, `base_path` ("parent directory where the worktree should be created"), `isolation` ("worktree" | "background"). NOTE: two fetches of the hooks page disagreed on field names (one said `worktree_name`/`branch`/`isolation_mode`); the doc's own JSON example uses `name`/`base_path`/`isolation`. Have the hook log stdin once to confirm. UNCONFIRMED which is right.
- **Output**: command hook must print ONLY the absolute path of the created worktree as a single line on stdout (diagnostics to stderr). Not JSON. HTTP hooks instead return `hookSpecificOutput.worktreePath`. Any non-zero exit, or no path, fails creation and the session/subagent does not start. No matchers; fires every time.
- **Hook must create the dir itself** (git worktree add, clone, whatever); `.worktreeinclude` is NOT processed with a hook (copy files in the script). Doc example script uses `$1`/`$2` args but the stated contract is stdin JSON; parse stdin with jq (SVN example uses `jq -r .name`).
- **Path constraint**: a hook-created dir with no git metadata passes Claude's identity check ONLY if no git repository contains it ("have the hook create its directories outside any repository"). A hook dir inside the repo (e.g. `.worktrees/x` or `.claude/worktrees/x`) with a real `git worktree add` has git metadata; the doc says only that a dir whose `.git` resolves into the main checkout is refused. A genuine linked worktree (own `.git` file pointing to `.git/worktrees/x`) is the normal case and should pass. Refuses if the worktree path CONTAINS the main checkout, if a `.claude`/`.claude/worktrees` path is a symlink, or if recorded path has a "network spelling" (UNC) on resume. So an ext4 path via WSL is fine from Linux side; `\\wsl$` paths would be refused for resume.
- **`WorktreeRemove` hook**: input `worktree_path`, `isolation`; fires ONLY for worktrees your WorktreeCreate hook created (since v2.1.214); exit code is the only control; JSON ignored; non-zero fails removal if the dir still exists.
- **Cleanup of hook-made worktrees**: Claude's periodic sweep (older than `cleanupPeriodDays`) keeps any worktree lacking its git-metadata marker, "including a worktree a WorktreeCreate hook created" -> hook worktrees are NEVER swept automatically; WorktreeRemove (on subagent finish / session exit) is the only cleanup. Subagent finishing without changes: default path removes automatically; with changes it stays until sweep.
- **Settings (any scope)**: `worktree.baseRef` (worktrees page: `"fresh"` default = remote default branch, `"head"` = local HEAD; settings-reference page says `"remote"`/`"local"` -- docs inconsistent, UNCONFIRMED which string is accepted), `worktree.sparsePaths` (array of dirs; default unset = full checkout), `worktree.symlinkDirectories` (array; symlink large dirs instead of duplicating), `worktree.bgIsolation` (bool). NO setting for base directory; relocation requires the hook. Default location `.claude/worktrees/<name>/`, branch `worktree-<name>`.
- Other: default creation skips repo-config filter drivers (LFS pointers); fetches origin default branch (5 s cap, if not fetched in 24 h) for "fresh" base; named worktree reuse; `.worktreeinclude` (gitignore syntax) for default path only.
- Isolation enforcement: while in a worktree Claude blocks Edit/Write targeting the main checkout and Bash cwd/`git -C` redirects into it. Subagent worktrees at default location do not load worktree-root CLAUDE.md/.claude/rules.
- Changelog (github CHANGELOG fetch returned 503): UNCONFIRMED for version history beyond the in-doc notes (v2.1.214 WorktreeRemove scope; v2.1.208 fresh-base fetch; v2.1.212 symlink refusal).


## 2. jj (Jujutsu) for concurrent agents
- Current release v0.45.1, published 2026-09-03 (https://api.github.com/repos/jj-vcs/jj/releases/latest).
- **Workspaces**: `jj workspace add` gives multiple working copies backed by one repo (https://docs.jj-vcs.dev/latest/working-copy/). A working copy goes **stale** when another workspace rewrites its commit; `jj workspace update-stale` recovers (creates a recovery commit if the op is lost). Same page.
- **Concurrency**: lock-free op log; a command loads repo at latest operation and writes a new op with it as parent; multiple op heads are 3-way merged at view level, conflicts (e.g. bookmark moved two ways) recorded rather than failing (https://docs.jj-vcs.dev/latest/technical/concurrency/). Docs say distributed/shared storage use has "known bugs" and is not thoroughly tested, esp. colocated. Working-copy commit is snapshotted on EVERY jj command (even `jj status`).
- **Git compat** (https://docs.jj-vcs.dev/latest/git-compatibility/): git hooks and `.gitattributes` NOT implemented (so merge=union and filters are ignored by jj's own merges); submodules not in working copy; Git LFS unsupported; sparse checkout / git-worktree replaced by native equivalents. Colocated workspace is default and mixing jj and git commands is allowed, but docs warn of performance degradation on large repos from import/export on each command, and branch conflicts when interleaving; `--no-colocate` / `git.colocate=false` recommended for large repos. NOTE: git-side `git worktree` checkouts are invisible to jj ("There is no jj repo", per claude-jj-worktree README).
- **fsmonitor**: `fsmonitor.backend = "watchman"` supported; docs warn that on large repos it may make watchman fail and `jj status` slower; tune inotify limits (https://docs.jj-vcs.dev/latest/config/). On drvfs (9p/NTFS) inotify does not see Windows-side changes: UNCONFIRMED for jj specifically. Default `snapshot.max-new-file-size` blocks big new files (set 0 to disable).
- **Perf at ~30k files on WSL/drvfs**: no source found. UNCONFIRMED.
- **Agent reports**: CodeAlive-AI/jj-agentic-workflow (https://github.com/CodeAlive-AI/jj-agentic-workflow; developed vs jj 0.44.0, passes on 0.45.1) lists hazards: `jj undo`/`jj op restore` rewinds the whole repo view and silently reverts concurrent writers in other workspaces; no read-only commands (even `status` snapshots, absorbing stray files/secrets into the current change, visible in evolog); deleting a git ref with default config silently abandons commits; empty revset is not an error. It ships guarded wrappers + hooks. `claude-jj-worktree` plugin (https://github.com/jasagiri/claude-jj-worktree) implements exactly the WorktreeCreate/Remove hook: `jj workspace add` into `.claude/worktrees/<name>/`, prints abs path; Remove runs `jj workspace forget` + rm. Blog: https://slavakurilyak.com/posts/parallel-claude-code-with-jujutsu (2025-07, updated 2026-09): multiple workspaces needed for concurrent sessions.
- `jj git push`: safety claims UNCONFIRMED (not fetched).

## 3. git merge-tree --write-tree
Source: https://git-scm.com/docs/git-merge-tree (docs for git 2.52).
- Introduced in **git 2.38**; `--write-tree` is the default mode on modern git (old `--trivial-merge` deprecated). Does not touch index or worktree; works in a bare repo; does real merge-ort: renames, dir/file conflicts, recursive merge-base consolidation. `--merge-base=<tree-ish>`, `--stdin` (batch), `-z`, `--name-only`, `--no-messages`, `-X<opt>`, `--allow-unrelated-histories`.
- Output: line 1 = tree OID; on conflict, then conflicted-file-info lines (`<mode> <oid> <stage> <path>`) and informational messages. **Exit 0 clean, 1 conflicts**, other = error. With conflicts the tree OID still written (contains conflict-marked blobs). Doc warns: don't infer success from empty conflict list; check exit status.
- Canonical pattern (doc): `T=$(git merge-tree --write-tree A B) || conflict; C=$(git commit-tree $T -p A -p B -F msg); git update-ref refs/heads/A $C` (add the old value as 3rd arg of update-ref for compare-and-swap, standard git-update-ref feature, https://git-scm.com/docs/git-update-ref).
- Local merge-queue builds: no authoritative cited example found; GitHub's own queue is server-side. One agent-memory issue documents a plumbing recipe for conflict resolution when local merge is blocked: https://github.com/Prithpal-Sooriya/Cloud-Agent-Memory/issues/175. Treat "how people build queues" as UNCONFIRMED.
- Which `.gitattributes` merge-tree reads (bare, no worktree): gitattributes doc is silent (https://git-scm.com/docs/gitattributes); UNCONFIRMED, test empirically (incl. whether `$GIT_DIR/info/attributes` applies).

## 4. WSL2 drvfs vs ext4 for git
- Microsoft: "store your files in the WSL file system if you are working in a Linux command line"; use `/home/<user>/Project`, not `/mnt/c/...` (https://learn.microsoft.com/en-us/windows/wsl/filesystems). Same page: if working from Windows tools, store in Windows FS.
- Numbers (secondary, search-snippet level, not independently verified): ext4 ~9x faster throughput than /mnt/c via 9P (~1.0 GB/s vs ~110 MB/s), metadata ops ~60x faster (https://www.linkedin.com/pulse/optimizing-wsl2-claude-code-complete-performance-tuning-cooper-rlqzc); original issue https://github.com/microsoft/WSL/issues/4197 ; benchmark repo https://github.com/craigloewen-msft/WSL2Benchmarking ; other: https://vxlabs.com/2019/12/06/wsl2-io-measurements/
- Reverse direction (Windows app reading `\\wsl$` / `\\wsl.localhost`): also goes over 9P; GitHub Desktop issue reports WSL repos 10-20x slower than native Windows repos for git ops (https://github.com/desktop/desktop/issues/22044). Defender scans via 9P; exclude distro path if heavy (same results). VS long open delays reported. No measurement for a game/.NET build reading Mods from `\\wsl$`: UNCONFIRMED. Reliability: Claude Code itself refuses to resume into a worktree whose recorded path has a "network spelling" (worktrees page), a hint UNC paths are treated as unreliable.
- Implication: keep the game's `C:\...\Mods` as a deploy TARGET (copy/robocopy from ext4), do not have it read from `\\wsl$`.

## 5. Multi-agent git practice 2025-2026
- Plain worktrees: pain points are per-worktree deps/services/ports and disk (one user: 9.82 GB across two worktrees for a ~2 GB codebase) per Trigger.dev, who moved to GitButler virtual branches (https://trigger.dev/blog/parallel-agents-gitbutler). GitButler: multiple branches applied to ONE working directory, Claude Code hooks assign each session's changes to a branch; breaks down when agents touch the same files, need different builds, or tests share state.
- container-use (Dagger): each agent gets a container + its own git branch, MCP server/CLI, git-based review (https://github.com/dagger/container-use ; https://dagger.io/blog/agent-container-use/).
- Worktree guides: https://www.augmentcode.com/guides/git-worktrees-parallel-ai-agent-execution
- jj-based: see section 2 (workspace per agent via WorktreeCreate hook).
- Claude Code native: worktree isolation + periodic sweep + `cleanupPeriodDays`; sparsePaths/symlinkDirectories for big repos (section 1). Graphite / "one integrator" / local merge-queue specifics: not researched in depth, UNCONFIRMED.

## 6. merge=union and git rerere
- Built-in `union` driver: "3-way file level merge for text files, but take lines from both versions... tends to leave the added lines in the resulting file in random order... Do not use this if you do not understand the implications" (https://git-scm.com/docs/gitattributes).
- Field reports (search results, https://github.com/thestoryportal/arhugula-harness/pull/1563 "merge=union is unsound for the append-only ledgers"; https://github.com/paiml/aprender/pull/3309; https://github.com/spec-kitty/spec-kitty/issues/4143): (a) rows must be independent as well as append-only; a same-key row changed on both sides yields both rows, readers keying on last-wins silently get one; (b) never apply `*.jsonl` globally (golden/dataset files get duplicated rows); (c) the attribute is read from the side being merged into, so branches cut before the rule existed never use the driver (add/add conflicts); (d) only text-line semantics: markdown with edits to the same paragraph will be duplicated/interleaved, not conflict. Not suitable for JSON arrays or non-line-structured files. Cited pairing with rerere: https://github.com/JakeChampion/lang/pull/8849 (UNCONFIRMED details).
- rerere (https://git-scm.com/docs/git-rerere): `rerere.enabled=true`; cache in `.git/rr-cache/` (shared by all worktrees of that repo, since common dir; UNCONFIRMED from docs); auto-invoked by merge/commit/rebase; gc defaults 15 days unresolved / 60 days resolved; relies on conflict markers. It only helps repeated IDENTICAL conflicts, and does not help a union-resolved file (no conflict arises). Whether `git merge-tree` consults rerere: UNCONFIRMED (docs fetched do not say).
