## The system, in neutral terms
A software factory run by LLM agents. A "Maturation Pipeline" moves each product unit (a game mod, ~12 of them) through stages: design, preflight, offline build, blind challenge (tests written first by a blind agent), in-game acceptance, pre-human check, the owner's walk, passed. A deterministic Python program (the "Dispatch tick", a systemd timer every 60 s) reads per-unit state files and a config JSON and launches capped LLM agent runs (builders, stewards, judges, fixers) as detached systemd units. Other launch paths exist beside the tick: an autonomy step, steward chains, a Designer role chained by a separate dispatcher program, judges, road-back builders for failed checks, scheduled role runs.
Each unit has consumable allowances: judge "looks" granted by the owner, blind cycles per visit, automatic in-game runs per visit, steward runs per version, launch retries, chained design runs per day, refusal counts that trip alarms, and a per-stage spend ceiling. State lives in several places: per-unit JSON records and a markdown journal in the repo, an append-only event ledger (JSONL shards, published through git), a dispatch state file, a hold list JSON, config JSONs. Several git clones exist; changes land on origin through a publish script that runs tests (tens of seconds to minutes).
The operator is one human talking to one LLM "Conductor" agent, whose context tokens are scarce. Other agents are launched as helpers.

## What went wrong today (measured)
- The owner said stop work on one unit. Stopping it took the Conductor ~15 tool calls: the first hold mechanism (a journal line) blocked stage moves but not a builder launch, so the tick launched another run a minute later; the airtight hold (a JSON list) could not be published because a test pinned the list's exact contents.
- Runs launched without authorization, and runs killed by the stop, consumed the unit's allowances (including a one-time owner-granted judge look). There is no command to give one back or to mark a run void.
- There is no single pause switch known to cover every launch path, and no forecast of what will start next.
- To learn the state of one unit the Conductor ran ~6 commands with long output.

## What is wanted
A design for how humans and agents interact with this pipeline: reading state, pausing/resuming everything or one thing, switching items on and off, editing queues and order, changing any consumable, voiding runs, forecasting what will happen next, and making exceptions; all simple, one-line, near-instant, minimal output (LLM tokens are the scarce resource), deterministic, traceable, reproducible, testable, hard to get wrong, with no launch path able to bypass it. Also: what in the pipeline's architecture made this hard, and what structural change removes the cause rather than adding another layer.
