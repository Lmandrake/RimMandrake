## What the literature says

**Huntley's original** (ghuntley.com/ralph, July 2025):
- **The loop itself:** `while :; do cat PROMPT.md | claude ; done`.
- **One item per loop.** He says it twice.
- **State lives in three files:** `specs/` (what to build), `fix_plan.md` (the to-do list) and `AGENT.md` (how to build and test).
- **Fan-out is fine, but only one judge:** many helpers may search and read, but **only one runs build and test**. That one is the pushback that rejects bad work.
- **Two failure modes he names:** placeholder or "minimal" implementations, and duplicate implementations of something that already exists. That second one is exactly our "search `src/` first, we keep having already built it" rule.
- **The human "sits on the loop":** you don't steer each step. You watch, and when it goes off the rails you change the prompt or the specs.
- **"Loop"** (his January 2026 follow-up): deliberately one process, one repo, one task per loop.

**The repomirror field report:**
- Overnight loops made about 1,100 commits for a little under $800.
- When they "improved" the prompt to 1,500 words, the agent got "slower and dumber". Going back to 103 words fixed it.
- GPT's caution: that's one case, so it means "keep it focused", not "always 100 words".

**Clayton Farr's playbook** (mirrored by Huntley):
- It splits the loop into two modes. A **planning** pass compares the specs against the code and rewrites the plan; a **building** pass takes the top item.
- It caps the number of passes, and pushes after every pass.
- The pushback that rejects bad work is "tests, typechecks, lints, builds".

**Anthropic's own ralph-loop plugin:**
- It runs inside one session, with a hook feeding the same prompt back. So context **accumulates** rather than resetting.
- It stops on a pass limit or a "completion promise".
- Its README says it's **not good for work that needs human judgment or design decisions.**

**From memory, not verified:** Huntley ran Ralph for months to build his CURSED language, and has described several loops on one repo.

## The options for us

1. **Fresh process per pass vs. in-session loop.** The literature and your context worry point the same way: a fresh `claude -p` each pass. Context starts empty every time, so there's nothing to reset. The plugin's in-session version is the one that piles up context.
2. **One item per pass (Huntley) vs. one step per pass (your ratchet).**
   - One item per pass is the classic, with fewer cold starts. But a long item makes a long pass, and if that pass dies, the work goes with it.
   - Your step ratchet is an extension, not something the sources do. Its passes are shorter and safer, and a killed pass loses only one step. The cost is that each pass re-reads the files, which spends tokens on orientation.
   - **A middle option:** one item per pass, but the item carries a step checklist that a new pass resumes from if the last one died.
3. **Planning and building as separate modes (Farr), or a plan written by hand.** A planning pass that rewrites the plan from the specs keeps it honest without you maintaining it. It's also where your "current focus" rule would live.
4. **One judge vs. many.** Every source agrees on helpers for reading and searching, and one final build-and-test gate. GPT added that **the loop script, not the agent, must run that gate after the pass.** It only pushes if the gate passes, and that's what makes the ratchet honest.
5. **Two loops side by side.** Workable if they're split by area so they never touch the same files. The sources only touch on this lightly, and the claim I have is from memory.
