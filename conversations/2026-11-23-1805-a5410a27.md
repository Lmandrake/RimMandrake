## Can the bridge change the game's values live? Yes, largely, and a Fable design pass on it is running

**My answer before the design comes back** `[my engine knowledge, not read from the code today; ~85%]`
- **XML-loaded values are live objects in memory.** After load, every def is an ordinary C# object. The bridge can write a field by reflection, which is what RIMMSqol does. Our bridge already reads def fields this way; it has no write.
- **What needs care:** some values are cached or copied.
  - A stat may be cached and need its cache cleared.
  - Some values are copied into each thing when it spawns, so only new things change.
  - Graphics are built once.

  The design pass must produce the table of which is which, read from the engine.
- **C# parameters:** static and instance fields can be poked the same way. A `const` cannot, because the compiler has already written its value into every caller. So our own mods should keep every tuning number in a field that is read at use time. That makes parameter sweeps free of rebuilds by design.
- **Behaviour, not only numbers:** a Harmony patch can be added or removed while the game runs. Loading a freshly compiled DLL beside the old one is possible but risky, because the game cannot unload the old copy.
- **One history to respect:** we retired a "reload the XML defs live" tool on 2026-09-03 after it hung a 589-mod game and broke pawn generation. Writing one field is a much smaller act than reloading whole defs, and the designer must say exactly how its design differs.

**The danger the design must guard against:** a result reached under live-changed values must never count as a result of the shipped build.
