## The design draft

I call the capability a **work bundle**: all the ready tickets of one system (one mod, or one pipeline component), worked by one run in one context, from the reality check to the live proof. **What a bundle run does**
1. **Reality sort, by a program, at no token cost.** Each ticket's acceptance test runs on the current build. A green test closes the ticket as already fixed.
2. **Read the system once and class every ticket:** real, already fixed, or not worth the touch. Group tickets with one cause, and put investigations first so one informs the next.
3. **Tests first, together.** Every real ticket has its acceptance test, and one red run covers the set.
4. **Fix in order.** After each ticket or one-cause group: a green run, a progress note and a publish, so a death loses one group at most.
5. **One fresh reader** reads the changed files once at the end, not once per fix.
6. **One live pass on a free game.** It runs the in-game checks the changes touch, and tries the tickets the sort kept but doubted.
7. **Each ticket closes with the commit that fixed it.** Tickets keep their identity and their test.

**Right size**
- No fixed count. The danger is a full context, and the evidence is 480k of context after 18 tickets.
- After each group the run reads its own context size. Above half its window, it finishes the group, writes a handover note, and a fresh run continues the bundle.
- My first estimate is 10 to 15 real fixes per context [guess ~60%]. The first three bundles would measure it.
- Tickets of two different systems never share a bundle.

**Where it goes**
- **Workshop Pipeline:** tickets already carry a home (FlowWorks holds 65, art canon 30). The launcher starts one bundle per home.
- **Maturation Pipeline:** a tester fixes what it finds. What it cannot fix goes into the mod's one bundle. A visit's failures route back as one bundle, not one fixer run per fault.
