## The route to build (the Conductor's design)
Call the new run an **onboarding run**. One onboarding run takes one home.

**Start, by program.** When a host has room, the lane picks one home that has old tickets and no live work bundle.
The lane launches one onboarding run for that home. The members are all the open old tickets of that home that are
not blocked, not waiting on a date, not switched off, not held and not under a live lease. A ticket of that home that
already has an outcome check joins the same run, as it does today. No hand names a ticket.

**Step A in the run: the reality sort.** The run reads every member against the code of now, before it writes any
check. The run gives each member one class and acts on it at once:
- done already: close the ticket, and name the commit that did the work;
- dead or stale (its target is gone, or a later ruling replaced it): drop the ticket with the reason;
- duplicate: supersede the ticket;
- not worth the touch (test 1 of `CLAUDE.md` §Touching code has a cost): drop the ticket with
  `not worth the touch: <why>`;
- needs the owner, the Conductor or a judge: write the route with `rimflow shape <ID> --parts` and go on;
- keep: the ticket goes to step B.

**Step B in the run: group and write the checks.** The run groups the kept tickets by cause or by the files that the
fix changes. The run writes the outcome check of each kept ticket with `rimflow shape <ID> --parts`. Each check is
seen to fail on the current build before the fix. Each check has its `fooled_by` line. A ticket for which no check is
possible gets the line `Acceptance test: none, <reason>` and a route.

**Step C in the run: the work.** The same run fixes the kept tickets group by group, test first, as a work bundle
does today. When the context of the run fills, the run saves its state file and ends. The existing restart rule then starts a
fresh run on the first open member. Every member ends with an outcome on the bundle record.

**Which homes the program may start.** Put the classes of home that the program may start in
`list_dispatch.json`, as data:
- `pipeline:*` and `machine:*` homes: on.
- a `mod:*` home: on only when the mod is switched on in the Maturation Pipeline, is not held by the owner
  (`src/RimMandrake/rimflow/mod_owner_hold.json`) and has no live bundle. For such a mod, the mod's own bundle takes
  its old tickets through the same steps A, B and C. Today `work_bundle.mod_members` leaves out a ticket with no
  test; 66 of 67 FlowWorks tickets had none on 2026-11-24.
- `game:*` homes: off. The owner held the sort of the old game-needs tickets on 2026-11-23, and he has not lifted that
  hold. The code path is the same; only the data says off.
- A ticket with no home is not started. `list_home.py no-home` lists those tickets.

**Order.** The home with the most open old tickets goes first. `./pipe why <Mod>` prints what blocks a mod. If the
lane can read by program that a home holds a ticket that blocks a switched-on mod, that home goes before the others.

**The page.** The page `D:\ClaudeWork\rimmandrake\conductor\MATURATION_NOW.md` (written by `src/RimMandrake/Utils/maturation_nonmod.py`) shows each onboarding run: the home, the count of
members, and the count of each outcome so far.

**The tickets that the Conductor named by hand tonight.** Do not stop a Shape run that is live. A named ticket that
no run has started is a member of its home's onboarding run, like any other old ticket.
