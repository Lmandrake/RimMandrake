## Claude

They are two different things, Mandrake, and the build match checks only one of them.

**Design Version** is the set of bars a mod is building towards, for example Pyrelands 0.1.0. **Build** is the actual code that ran: the mod's commit, its deployed folder, the mod list and the game build.

The build match checker looks only at the build. Its question is whether this in-game pass came from the same code and mod list you are about to walk. It needs that because the code keeps changing while the mod works through its tickets: a pass recorded on Monday's code says nothing about Wednesday's. It does not care what the bars say.

Your real question is whether the version changes when we add or move bars. Today it does not, and that is a looseness worth seeing clearly:

- **This morning's card changed the bar set of Pyrelands 0.1.0 without changing its number.** The wind bar was added, two bars were reworded, and rain-fill and smoke moved to 0.2.0. The pipeline has a "re-pin" step for exactly this: a locked version changed by your card keeps its number, and only the affected bars are re-judged.
- **Your own versioning rule reads stricter than that.** It says a design that cannot pass because it is wrong "is superseded by a new version, not edited in place", and that additions belong to the next minor version.
- **What tracks the change today is the release-candidate count.** Each arrival at your walk is 0.1.0-rc.1, rc.2 and so on. So "0.1.0" names a target that can move by your card until it passes, and the rc number says which attempt you are looking at.

My view: before a version has ever passed, letting your card edit it in place is the practical choice. Otherwise every bar correction would mint a new version of something nobody has seen. But the pass record should then state exactly which bars it passed, by a hash of the bar set, so "Pyrelands 0.1.0 passed" can never mean two different things. I believe the pass record lists its bars already `[guess ~60%, not checked this turn]`; I can verify that if it matters to your decision.

So the checker stays simple either way: it compares builds. Whether a bar change before the first pass should bump the version number is a separate ruling, and it is yours.
