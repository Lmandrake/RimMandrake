4. The shared core: one append-only ledger per mod, one file per writer, so a holder cannot edit a judge's findings or the owner's words. Every other per-mod file becomes a view printed from it. 5. On the Conductor's addendum: no written "250k" lesson exists anywhere, so I measured it from 3,260 Relentless transcripts. In the 74 sessions that ran past 200k and landed anything, 208 of their 249 landings came after 200k, and 111 after 250k [measured]. A landing here is any publish, not necessarily a fix. So the holder is allowed to grow to about 600k, and rebuilding from the ledger is only the fallback after a forced restart.

**Three options**
- **A, the record is the holder:** stage runs still start fresh, but each one is the mod's named holder and starts from a short summary the ledger prints. Smallest change, but context is still lost at every stage.
- **B, a resumed per-mod session (recommended):** A's ledger plus one session per mod that the dispatcher resumes for each stage, rotating near 600k. The dispatcher already has resume code for windows, and B keeps the context the owner asked for without a window having to stay open.
- **C, a holder seat:** Foundry/Bench-style windows, each holding one mod, with the pipeline as their checklist. Least code, but the most attention, and window restarts measurably lose about 12% of what was owed.

**Recommendation:** B, built as A first, piloted on one mod with two mods advancing at once.
