## A live test declares its kind

Full text: `design/RimMandrake/standing_rulings.md` §Live tests have three kinds. How to write each row: `skills/live-debugging-proof-harness/SKILL.md` §The scene contract.
- A scene with no tag is kind A: one valid run decides PASS or FAIL. Never repeat an unchanged run to get a PASS.
- Kind B (stochastic) and kind C (an intermittent hunt) carry their evidence on the scene. Kind B passes on one SUCCESS, with no MOD FAILURE and no UNRESOLVED run on the same claim and build. A result that is random by design passes on its written X of Y. When its runs end short of X, stop: the scene is held, the pipeline asks the Conductor, and nobody else changes X or Y. All budgeted runs done with no SUCCESS: the verdict is INCONCLUSIVE. A hunt is never part of the exit. The tag is on the scene in the test table: `test_kind` ("A", "B", "C"; absent is A), `tag_evidence`, `budget` (runs, kind B) and `x_of_y` ([X, Y], a result that is random by design).
- Write `outcome` on every row: SUCCESS, MOD FAILURE, RANDOM MISS, ENVIRONMENT FAULT, APPARATUS FAULT, UNRESOLVED or COULD NOT LOOK. Only SUCCESS speaks for the mod. No other outcome needs a later pass to cancel it. One row per run. Beside it: `spoiled_by` on an ENVIRONMENT FAULT (what spoiled the run, and the record that shows it) and `forbidden` (the list of forbidden effects seen; `[]` for none). SUCCESS goes with verdict PASS. MOD FAILURE goes with FAIL and class MOD. Every other outcome goes with UNMEASURED; add class HARNESS or SITE to an APPARATUS FAULT only when the check or the scene itself is wrong.
- ENVIRONMENT FAULT only when the record shows that something outside the tested behaviour spoiled the opportunity. If the mod could have spoiled it: UNRESOLVED. A forbidden effect is a MOD FAILURE in any run. An UNRESOLVED run holds the scene's pass until someone classes it: that person adds to the row `classed`: `{"outcome", "why" (six words at least), "by"}`.
- A serious fault (one sighting), or a fault seen again, opens a hunt. A hunt never opens silently: a note `HUNT OPENED:` on your item and a line in the Conductor log. One command writes both: `python3 src/RimMandrake/rimflow/hunt_open.py <your item> --what ... --why-it-matters ... --next-step ... --cost ...`.
- When a run names a thing that spoiled it, try to remove that thing. Lean towards building the control.
- No exit asks for every scene in one visit, or for one scene several times in a row.

## A FAIL is diagnosed and classed in the sitting

A FAIL or UNMEASURED is not a verdict to carry home bare: diagnose it by experiment while the game is up (change one thing, watch the row), and class it.

**Class each failed or UNMEASURED line first** (owner, 2026-11-20; `design/RimMandrake/standing_rulings.md` §Touching code has a cost): mod wrong (`class` MOD: the mod's code, defs or settings), check wrong (`class` HARNESS: the script, the instrument, the criterion) or scene wrong (`class` SITE: the staged scene). Then:
- Test 1, the worth of the touch: a wrong check or scene is worth repair only if a bar would go undecided without it. "A failure happened" does not make it worth the touch by itself: the failure was the check's. A check that no bar needs is not kept: remove it from the test table (and delete it when nothing else names it), with one line on the polish list as the record of the removal. No ticket. A needless check left in place meets the next judge again.
- Test 2, if you see it, do it: the agent that classes a check or scene wrong repairs it in the same sitting and runs it again. "My verdict must stay independent" and "my assigned work would not finish" do not excuse a wrong check or scene: its repair does not touch the mod.
- The guard: a repaired check counts only after it is seen to FAIL on a planted fault (or on a state known bad) and PASS on the real build, in that sitting, with both readings recorded beside the row. A needed check whose repair cannot be shown both ways stays not counted (UNMEASURED), never PASS, and keeps an owner: this run, or a filed item with the evidence. To plant, use what exists: a planted case of the blind challenge (`lane2/planted_faults.json`, `plant_faults.py`), the check's own `--old` or mutant switch, or a save or state known bad. Build no new framework.
- A repair never weakens what the check observes, and never touches the mod.
- **Mod wrong, and you can fix it: fix it in the sitting.** Write a before/after test (red on the parent, green on the fix), fix the mod, and show the check passing on the fixed build. Then one fresh reader, a run that did not make the fix, reads only that fix, once (owner, 2026-11-20). Only a mod fault you could not fix in the sitting goes down the road back, with the evidence why (no tools, the fix is not known, another run holds the files, it needs one of his five acts or a north-star bar).
- **A run that edits a deciding test records its red run before it closes:** `python3 src/RimMandrake/rimflow/maturation.py red-seen <Mod> <test id> --patch <the planted fault's patch>`, for each decider in a file you changed (one edit to a shared test file invalidates every decider in it). A certificate refuses an edited decider with no recorded red run, and the mod waits until one is recorded.
- A wrong check or scene never sends the mod back a stage. Only a mod wrong line not fixed in the sitting, or a bar left undecided, does.
- **A fix that needs the live game takes it when it is free** (owner, 2026-11-20): there are several games, each with its own bridge holder: ArchBig (Steam's install on Archmagi, his full list), ArchSmall (its own install on Archmagi), and Steve1 and Steve2 on SteveDesktop. Take any game whose bridge is free, ours, or stale by the 45-minute rule, with `python3 src/RimMandrake/rimflow/cli.py bridge take --idle-ok --for "<what>" --seat BENCH` and `./game --idle-ok --why "<what>" up`; for ArchSmall run `eval "$(python3 src/RimMandrake/Utils/game_instance.py env ArchSmall)"` first (a bare `RM_GAME_INSTANCE=b` does not reach a `python.exe` tool, which then drives ArchBig; deploy with `--instance ArchSmall`) and start it if it is down (`python3 src/RimMandrake/Utils/game_instance.py launch ArchSmall --wait`). If ArchBig is busy or held, use ArchSmall; only a check that needs his full list waits for ArchBig, and then say so by name. Release it the moment the work stops (`python3 src/RimMandrake/rimflow/cli.py bridge release --seat BENCH`). His OWNER hold, the `./bridge` override, no flyer flight, and never fullscreen or focus a game still bind. A mod does not wait a stage for a game that sits unused, and no line says "waiting for the live game": name the game and why no other game can take the work.

What each class does here (`read_ingame_exit` reads these row fields):
- **Mod wrong, and you can fix it** (`class: "MOD"` on the failed row): fix it in the sitting. Write the before/after test first and see it red on the parent, fix the mod, see it green, commit, redeploy, and re-run the checks that the fix touches on the fixed build (`build_match.py check` names them; every other row still counts). Write the re-run row of this check with `mod_fix`: `{"commit": <sha>, "unit": <your unit>, "red": {"cmd": ..., "rc": <non-zero>, "on": <parent>}, "green": {"cmd": ..., "rc": 0, "on": <sha>}}`. Then one fresh reader, a run that did not make the fix, reads only that fix, once, and writes `design/concepts/Pyrelands/version/in_game/visit_8/fix_reviews.jsonl` (`{"fix": <sha>, "reader": <its unit>, "verdict": "sound"|"unsound", "why"}`); the steward run that reads this visit is that reader. Never write that file yourself.
- **Mod wrong, and you cannot fix it in the sitting**: the row stays FAIL; say why on the row (`unfixed`: no tools, the fix is not known, another run holds the files, one of his five acts, a north-star bar). It goes down its road back (spec Stage 6: the lowest stage that can show it, an offline test that fails on the old code first), and a new visit reruns it on the fixed build.
- **Check or scene wrong, and a bar needs it** (`class: "HARNESS"` or `"SITE"` on the failed row): repair the check or the scene, commit the repair, keep the deployed build (the rows keep its `mod_sha`), plant the fault and run the repaired check on it, then run it on the real build. Write the re-run row with `repair`: `{"class": "HARNESS"|"SITE", "commit": <sha>, "planted": {"plant": <what you planted>, "command": ..., "verdict": "FAIL", "evidence": <path>}}`; that row's own PASS is the real-build reading. The earlier HARNESS or SITE row spends nothing. No item. When no plant exists, or you cannot repair it, the row says `unrepaired` (why) and `owner` (your item, or the item you file with the evidence): the check is not counted and its bar reads undecided.
- **Check or scene wrong, and no bar needs it** (another check decides each of its bars): remove it from the test table (`design/concepts/Pyrelands/version/test_table.json`: the entry, and its id in each bar's `decides`), delete its code when nothing else names it, and write one line on `design/concepts/Pyrelands/version/in_game/visit_8/polish.md` as the record. No item. The exit reads a needless check left in the table as not met.
- A FAIL or UNMEASURED row with no class never passes: the exit reads it not met. A spoiled run needs no class and no later PASS: with no valid run beside it, its line reads `spoiled` and the scene runs again.
- **File your own failures before you end**, while you hold them: each line that still goes back (a mod fault you could not fix, a needed check not counted) is one named rimflow item, `--caused-by` your item, with its acceptance test (red now, green on a fix) and what you found; write its id on the row as `filed`. The road back starts from your items; no router run rebuilds them.
