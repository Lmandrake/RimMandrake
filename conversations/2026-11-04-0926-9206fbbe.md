Mandrake, a local GitLab wouldn't help with conflicts. A local plain git repo would help somewhat, and what would really help is one process that lands every commit in turn.

**Where our conflicts come from.** Most of the machinery (`./publish`, `land.sh`, `seat_sync.py`, the belt, the sharded ledger) works around two problems:
1. **Two writers change the same file.** That happens wherever the files are hosted. Splitting the ledger into one file per seat was the right fix for that, and nothing about hosting changes it.
2. **Racing to push.** Two clones each fetch, rebase and push. Whoever is second is refused and has to go round again. Each push to GitHub takes a second or more over SSH, and more on a bad day, so with 8 workers, 16 clones and the timers all landing, they collide often.

**What a local repo changes.** It shrinks the second problem only. A push to a repo on the same disk takes milliseconds, so the chance of two pushes overlapping falls a lot, and so does the retry churn. It does nothing for the first problem.

**What GitLab adds on top.** GitLab's merge trains are a real answer to the race: changes queue up and land one at a time, each tested on top of the last. GitHub has the same thing (its merge queue). But both work only through merge requests or pull requests, and our agents push straight to `main`. To use either, every agent would have to open a merge request and wait for it, which would slow us down. GitLab also runs Postgres, Redis and Rails, which want roughly 4 to 8 GB of memory, in a WSL that already sits around 20 GB used with Relentless running. That's a lot of heavy machinery for a feature we'd use only in an awkward way.

**What would actually remove the race.** Give us one lander. Agents commit locally and hand the commit to a single process that rebases each one onto `main` in turn, runs the quick checks, and pushes. With only one writer to `main`, a push can never be refused for being behind. Two agents changing the same lines would still show up, now as a clear "your change didn't apply" back to that agent instead of a retry loop. This is the core of GitLab's merge trains without GitLab. Put it in front of the local bare repo from my last answer and you get both the fast pushes and the end of the race, while GitHub becomes a mirror.

**My assessment of the idea.** It's the right question to ask, since conflict handling really is a large part of our tooling. GitLab is the wrong tool for it, though: heavy, and its fix needs a merge-request workflow we don't use. A single lander plus a local bare repo is a standard pattern and moderately complex. The risk is in moving `./publish`, `land.sh` and `seat_sync.py` over without stranding work. In return, much of the conflict-handling code could eventually be deleted.

That last point is a guess. I haven't measured how often pushes are refused today, and that number tells us whether this is worth building.
