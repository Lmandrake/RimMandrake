## Why agents don't use branches

**We tried branches, and they made things worse.** In late September every agent got its own worktree and branch: Claude Code's built-in isolation. Within about a week, as measured on 2026-10-01:
- there were **132 worktrees and 146 branches**;
- **68 branches were never merged back, holding 257 commits of finished work** that never reached main;
- `/tmp` filled to 100%;
- throughput fell from **268 to 178 commits a day**;
- the share of commits that were just recovering lost work nearly doubled.

On 2026-10-02 you turned worktrees off by question card. The stranded work was saved as 112 `archive/*` tags on GitHub, so it is reachable, but none of it was ever accepted into main.

**The underlying point:** a branch doesn't prevent a clash. It postpones the clash until merge time and moves it to a moment when nobody is watching. Agents are good at making branches and bad at merging them back, so the work piles up off to the side.

## What actually caused our clashes, and what fixed each one

| What went wrong | Would branches have helped? | What fixed it |
|---|---|---|
| **Many agents writing in one folder.** 215 files lost on 09-25, a `reset --hard` that ate staged files, a peer's `checkout -- src` | No. Branches share the one folder and its staging area. | **One writer per clone**: each seat (window) has its own copy of the repo. |
| **Everyone editing the same busy files**: the ledger, queue pages, DLLs | No. The same lines conflict, just later, at merge time. | Changing how the data is stored: one append-only file per seat, auto-merged by git (`merge=union`), queue pages generated on read instead of committed, one writer for DLLs. Measured: **24 conflicts per test run → 0**. |
| **Slow Windows drive**: `git status` took 10–12 s | No | Working copies moved to Linux disk (ext4): 0.04 s. |
| Real conflicts in source code | No: git raises those either way | Rare now, and they come up immediately, in a folder with one owner. |

## Branches, worktrees, clones, and the rest

- **Branch:** a name pointing at a line of commits. It costs nothing to make, but it gives no isolation: everything working on that folder shares one working directory and one staging area. Good for long-running experiments and human review (pull requests). Bad for agents, who strand them.
- **Worktree:** a second working folder that shares one repo, each folder on its own branch. Cheap on disk, and it does isolate files. Our history: 132 of them, mostly on the slow Windows drive. Branches got stranded, and dirty worktrees couldn't be removed without `--force`, which is forbidden. **Turned off, and blocked by a hook.**
- **Full clone:** a complete separate copy with its own history store, branch names and staging-area lock. This is the strongest isolation, with no lock contention between seats. It costs about 3 GB, and 7–14 GB for a throwaway one. In October, 18 forgotten clones filled 276 GB, so Relentless now has a **pool capped at 16 clones / 70 GB**, reused rather than recreated, with an alarm on any clone holding unlanded work. A shared history store (`store.git`, `--reference`) makes new clones cheaper.
- **Stash:** banned. A `--autostash` stranded 53 files on 10-10.
- **Landing with `./publish`:** git's low-level commands (`merge-tree`, `commit-tree`) put one commit on top of the latest main and push it, retrying up to 8 times if main moved. It never stashes and never touches anyone else's files. **This is how pushes happen often:** small commits, each landed within minutes.
- **The `D:\` mirror:** a read-only export of main for Windows tools. Nobody writes to it.
- **Considered and deferred:** Jujutsu, a newer version-control tool ("not now", with a condition for revisiting it), and helpers handing work in on `submit/` branches (you approved that, but it isn't in use).

What failed here was **long-lived** branches that need someone to merge them later. Agents leave those stranded. We measured it: 257 commits that never made it back.
